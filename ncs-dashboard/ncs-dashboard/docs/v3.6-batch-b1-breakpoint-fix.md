# Batch B.1 · 响应式断点缺陷诊断与修正

> 触发问题：视口在 **1715×1401** 附近继续变窄时，页面看似「不再响应式变化」，
> 信息从右侧开始丢失。
>
> 本文档基于 **4 个独立诊断脚本 + 17 档视口实测**，先定位根因，再给修正方案。
> 结论与 ChatGPT 的外部评审有出入，已逐条核实并标注。

---

## 第 1 章 · 复现与实测

### 1.1 首先确认一个事实：1715×1401 判定为 `reflow`

```text
ratio      = 1715 / 1401 = 1.2241
designRatio= 16 / 9      = 1.7778
ratioDiff  = |1.2241 − 1.7778| / 1.7778 = 0.3114
阈值        = 0.30
⇒ 0.3114 > 0.30 ⇒ mode = reflow
```

所以 **它不是 scale，也不是 compact**。ChatGPT 推测「实际可能卡在 compact」——
推测方向合理，但实测数据表明它**已经正确落到了 reflow**，不存在卡档。

### 1.2 那「页面不变」是怎么回事？——实测

固定高度 1401，宽度从 1715 连续收缩到 1100，逐档测量 `.dashboard-grid` 与三列：

| 宽度 | mode | grid 宽 | 三列宽 |
|---|---|---|---|
| 1715 | reflow | 1695 | 1695 / 1695 / 1695 |
| 1600 | reflow | 1580 | 1580 / 1580 / 1580 |
| 1500 | reflow | 1480 | 1480 / 1480 / 1480 |
| 1400 | reflow | 1380 | 1380 / 1380 / 1380 |
| 1300 | reflow | 1280 | 1280 / 1280 / 1280 |
| 1200 | reflow | 1180 | 1180 / 1180 / 1180 |
| 1100 | reflow | 1080 | 1080 / 1080 / 1080 |

**列宽每一档都在跟着变**（1695 → 1580 → 1480 → …），并非「卡住不动」。

同时逐元素检测溢出：

```text
实测 17 档视口，document.documentElement.scrollWidth === clientWidth
超出视口右边界的元素数量 = 0
```

⇒ **不存在真实裁切**。「信息从右侧丢失」是**观感**，不是 CSS 溢出。

**观感来源**：reflow 是单列纵向布局（`flex-direction: column`）。
宽度变化只影响「每一列多宽」，不影响「有几列、怎么排」。
与 scale 模式（画布等比缩放）相比，reflow 在宽度变化时**结构完全不变**，
所以连续拖拽窗口时会觉得「它怎么都不动」。

### 1.3 但确实发现了两个真 bug

#### Bug A：`ratioDiff` 关于 1.7778 对称，导致模式出现顺序颠倒

`|w/h − 16/9|` 是**绝对值**，所以「比 16:9 更扁」和「比 16:9 更高」被判为同等偏离。
后果是 **compact 会出现在比 scale 更宽的宽度上**。

以高度 1401 为例，解出各模式的宽度区间：

```text
scale   : ratioDiff ≤ 0.15 → w/h ∈ [1.511, 2.044] → w ∈ [2117, 2864]
compact : 0.15 < rd ≤ 0.30 → w/h ∈ (2.044, 2.311] → w ∈ (2864, 3238]
reflow  : 其余
```

展开成完整数轴：

```text
w <  2117   →  reflow
2117 ~ 2864 →  scale
2864 ~ 3238 →  compact   ← 比 scale 还宽！模式顺序被颠倒
w >  3238   →  reflow
```

**同一个「compact」在一个比 scale 更宽的区间里出现**，这在语义上是矛盾的：
compact 定义是「空间不够、需要退化布局」，结果它却需要更大的窗口宽度。

> 根因形式化：`ratioDiff` 在宽度上是「V 形」的（在 16:9 处取 0，两侧同时上升）。
> 固定高度增大宽度时它先降后升，所以**任何双侧阈值都必然产生
> `compact → scale → compact`** 的非单调序列。

#### Bug B：竖向窗口下 compact 几乎不可达

由 1.3 的公式可见，模式区间**随高度剧烈漂移**：

| 视口高度 | compact 出现的宽度区间 |
|---|---|
| 1080（标准 16:9） | 1067 ~ 1463 |
| 1200 | 1185 ~ 1625 |
| **1401（用户场景）** | **2864 ~ 3238** |
| 1600 | 3271 ~ 3698 |

高度一旦超过 ~1200，compact 就漂到 2864px 以上——那是超宽屏范围，
而**桌面窗口在竖向拉高时恰恰最需要 compact**。需求与判定完全反向。

#### Bug C（实施期新发现）：compact 只有一种形态，竖向高窗被压成横条

修正 Bug A/B 后，`1715×1401` 能正确进入 compact 了，但**截图实测暴露出第三个问题**：

Batch B 的 compact 只有一种形态——中心组 `flex: 0 0 100%` 全宽置顶 +
左右两列 50/50 并排。这在 1280×1024、1024×768 这类**矮而窄**的窗口里是对的；
但在 1715×1401 这类**竖向高窗**里，横向其实够放三列、纵向还大量富余，
强制中心组全宽置顶会得到：

```text
.dashboard-page  被撑到 2270px（视口只有 1401）→ 必须滚动
中心组宽 1687px，其内两张图被 minmax(320px,1fr) 拉成  1669 × 339
                                              宽高比 4.92 : 1  ← 一条横条
对比 1920×1080 下同样两张图：                  791 × 390  宽高比 2.03 : 1
```

⇒ 图表的宽高比从 2.03 恶化到 **4.92**，折线/热力图的空间信息严重失真，
页面还要滚动 869px 才能看全。**这才是用户所说的「信息从右侧开始不断丢失」
的底层成因**：不是真的裁切（实测 0 溢出），而是**结构降级过度**导致的
视觉失真 + 纵向溢出。

### 1.4 为什么 12 个样本没查出问题

`verify-layout.mjs` 的 12 个样本全部是**常见的屏幕分辨率组合**
（1920×1080、1366×768、1024×768…），它们的 w/h 比值恰好分散在两个区间边缘，
**没有覆盖「同一高度下连续改变宽度」这条路径**，因此漏掉了 1.3 的两个 bug。

⇒ 这是测试样本设计的问题：**只测了「分辨率」，没测「窗口连续拖拽」**。

同时它也**没有校验几何结果** ——「模式判定对不对」和
「该模式下图表宽高比是否健康」是两个独立的断言，原有脚本只做了前者。

**分歧点**：ChatGPT 把问题归因于「模式判定错误 + CSS 固定宽度」；

1. 判定只用比值、不用绝对尺寸（→ Bug B）；
2. 比值取绝对值导致模式顺序颠倒（→ Bug A）；
3. **compact 只有一种形态**，竖向高窗被压成 4.92:1 的横条（→ Bug C，
   这条是实施期通过截图才发现的，ChatGPT 与我的首轮诊断都没预见）。

ChatGPT 提出的「宽度断点」方向是对的，但**单独用宽度断点无法同时满足
约束 A（1920×1080→scale）与 B（1715×1401→compact）** ——
因为这两者的差别只在比例上（1.778 vs 1.224），
纯宽度条件把它们判成同一档。最终解法必须是 `h ≤ k·w` 这种双变量形式（见 3.2）。

## 第 3 章 · 修正方案

> 本章记录**实际采用的方案**。中途试过三版基于「比例 + 绝对宽度」的组合，
> 全部被自己的不变式测试否决（见 3.5 的「失败版本归档」），
> 最终解法在 3.2 给出。

### 3.1 核心约束：四条硬约束必须同时成立

| # | 约束 | 理由 |
|---|---|---|
| A | `1920×1080 → scale` | 设计基准，必须走等比缩放 |
| B | `1715×1401 → compact` | 竖向窗口，缩放会浪费 31% 面积且字缩到 0.893× |
| C | `2560×1440 → scale` | 2K 屏的视觉体验与 1080p 一致 |
| D | `3840×2160 → scale` | 同上，4K |
| ★ | **单调性** | 对任意固定高度，更宽的窗口不得拿到更「退化」的模式 |

### 3.2 关键洞察：为什么「绝对高度上限」和「比例」都不行

**方案甲：绝对高度上限（`h ≤ 1000 → scale`）**

```text
1920×1080 → h=1080 > 1000 → compact   ❌ 打破设计基准
```

**方案乙：单侧比例（`w/h ≥ 1.6 → scale`）**

```text
1920×1080 → 1.778 ≥ 1.6 → scale  ✅
1715×1401 → 1.224 < 1.6 → compact ✅
但 1600×1200 → 1.333 → compact；而 1280×1024 → 1.25 → compact
问题：固定高度下 w/h 随宽度单调增，看似没问题；
     但 3440×1440（21:9, ratio 2.389）与 1920×1200（16:10, 1.6）都被拖进 scale，
     而真正的「竖向桌面窗口」区间被压得极窄。
```

**真正的解法：让高度上限随宽度浮动**

```text
高度 ≤ k × 宽度     ⇔    宽度 / 高度 ≥ 1/k     ⇔    scale
```

这是**同时依赖 w 与 h** 的条件，但它对「固定高度扫描宽度」是单调的：

```text
高度 h 固定，宽度 w 增大
  ⇒ 右侧 k·w 单调增大
  ⇒ 条件 `h ≤ k·w` 只会从「不满足」翻到「满足」，永不回退
  ⇒ 单调性保住 ✅
```

而它又能区分竖向窗口：`1715×1401` 的 `h/w = 0.817`，
`1920×1080` 的 `h/w = 0.5625` —— **k 夹在两者之间即可同时满足 A 与 B**。

### 3.3 最终断点定义

```js
export const BREAKPOINTS = Object.freeze({
  //   宽度 < 900                    → reflow
  //   900 ≤ 宽度 < 1180             → compact
  //   宽度 ≥ 1180 且 高度 ≤ 0.7·宽度 → scale
  //   宽度 ≥ 1180 且 高度 > 0.7·宽度 → compact
  reflowMaxWidth: 900,
  compactMaxWidth: 1180,
  // scale 的纵向准入系数：等价于「宽高比 ≥ 1/0.7 ≈ 1.4286」
  scaleHeightRatio: 0.7,
  // compact 内部的纵向分档（见 3.4）
  compactColumnMinHeight: 960,

  designWidth: 1920,
  designHeight: 1080
})
```

### 3.4 `k = 0.7` 的由来

k 的可行区间由约束 A 与 B 夹出：

```text
约束 A：1080 ≤ k × 1920   ⇒  k ≥ 1080/1920 = 0.5625
约束 B：1401 >  k × 1715   ⇒  k <  1401/1715 = 0.8169
⇒ k ∈ [0.5625, 0.8169)
```

取 **0.7**（区间中点附近），两侧余量充足。复核四个硬约束：

| 尺寸 | `h ≤ 0.7·w` | 判定 | 期望 |
|---|---|---|---|
| 1920×1080 | 1080 ≤ 1344 ✅ | scale | scale ✅ |
| 1715×1401 | 1401 ≤ 1200.5 ❌ | compact | compact ✅ |
| 2560×1440 | 1440 ≤ 1792 ✅ | scale | scale ✅ |
| 3840×2160 | 2160 ≤ 2688 ✅ | scale | scale ✅ |
| 1600×1200（4:3） | 1200 ≤ 1120 ❌ | compact | — |
| 3440×1440（21:9） | 1440 ≤ 2408 ✅ | scale | — |

### 3.5 失败版本归档（为什么走不到「比例 + 绝对宽度」）

| 版本 | 做法 | 被否决原因 |
|---|---|---|
| v1 | `scaleMinWidth: 1180` + `scaleRatioTolerance: 0.12`，第四分支仍用 ratioDiff | 仍产出 `2180 compact / 2200 scale` 的顺序颠倒 —— 比例依旧把守边界 |
| v2 | `scaleMaxAspectRatio: 1.95`（单侧比例） | `1715×1401 → scale`（错，浪费 31% 面积）；且 `768→900` 处 7 处单调性违规 |
| v3 | `scaleMaxAspectRatio: 1.60` | `1920×1080 → compact`（严重回归）+ 11 处违规。根因：固定高度下 `w/h` 随宽度**单调增**，单侧比例检查本身就不单调 |
| v4 | `scaleMaxHeight: 1000`（绝对高度上限） | 单调性 0 违规 ✅ 但 `1920×1080 → compact` ❌ —— 2K/4K 也被打下去 |
| **最终** | **`h ≤ 0.7·w`（高度上限随宽度浮动）** | **0 违规 + 四条硬约束全通过** ✅ |

### 3.6 Compact 二段化：修复 Bug C

`h ≤ 0.7·w` 解决了「进不进 compact」，但进 compact 之后的**形态**还需要分档。
新增 `data-tier` 属性，只对 compact 有意义：

```js
function detectCompactTier(width, height) {
  if (!width || !height) return 'stack'
  return height >= BREAKPOINTS.compactColumnMinHeight ? 'columns' : 'stack'
}
```

| tier | 触发条件 | 形态 | 适用 |
|---|---|---|---|
| `columns` | `h ≥ 960` | **保留「中｜左｜右」三列**，高度由 `minmax(0,1fr)` 提供，图表回到 ~16:9 | 1715×1401、1600×1200、1280×1024、1024×1366 |
| `stack` | `h < 960` | Batch B 原形态：中心组全宽置顶 + 左右两列并排 | 1024×768、900×600 |

**960 的取法**：`columns` 需要的 page 高度 ≈ header(68) + KPI(≈209) + grid。
grid 的列高下限由右列决定（StationRanking 要放 10 行 + 3 个面板），
实测 1280×1024 下 grid=719px、中心组首行 ~370px 仍然健康，故取 960。
低于 960 时三列会被压得过矮，退回 stack 更合适。

> **实施细节（踩过的坑）**：`columns` 档必须同时给 `.dashboard-viewport`
> 一个**确定高度**（`height: 100vh`），否则 `.dashboard-page` 的
> `height: 100%` 会解析到 `auto`（父级只有 `min-height`），
> 回退为内容高度 —— 实测导致 1600×1200 下 page 被撑到 1450px、纵向溢出 250px。

### 3.7 同步加固：防溢出兜底（采纳 ChatGPT 第二优先项）

虽然实测当前无溢出，但为防 Batch C/D 引入新的固定宽度，统一加固：

```css
/* 所有响应式容器的直接子项强制 min-width:0，允许收缩 */
.dashboard-viewport .dashboard-grid,
.dashboard-viewport .dashboard-column,
.dashboard-viewport .kpi-strip {
  min-width: 0;
}
.dashboard-viewport .dashboard-column > *,
.dashboard-viewport .kpi-strip > *,
.dashboard-viewport .dashboard-grid > * {
  min-width: 0;
}
```

这是「防御性」而非「修复性」改动，注释中会写明。

### 3.8 补测试：单调性不变式 + 几何回归

`verify-layout.mjs` 新增两类断言，且**直接编译源码里的 `detectMode`**，
而不是复制一份同构实现（避免日后两份逻辑漂移）：

```js
// ① 不变式 I1：单调性
//    固定高度，宽度从 3200 递减到 600（步长 4），
//    合法序列的等级必须「非递增」（reflow < compact < scale）。
//    7 个高度 × 4557 次比较，0 违规。
// ② 不变式 I2：三档可达性
//    900 / 1080 / 1200 / 1401 / 1600 五个高度下三档均可达。
// ③ compact 双档分档正确性 + 双档可达性。
// ④ CSS 结构断言：columns 档存在且给 viewport 确定高度。
```

**核心不变式（新增断言）**：

```text
对任意高度 h，不存在 w1 < w2 使得
  mode(w1) = 'scale' 且 mode(w2) = 'compact'
即：更宽的窗口不应拿到更「退化」的模式。
```

这条断言直接锁死 Bug A。

另新增几何回归度量（`scripts/diag-compact.mjs`），
断言「任一尺寸下最扁的图表宽高比 ≤ 3.6」——
这把「模式判定」与「图表几何是否健康」绑在一起，覆盖 1.4 暴露的第二类测试盲区。
