## 第 2 章 · 技术争议的核实结论

这两轮讨论有三处技术分歧，我逐一做了核实。**结论：ChatGPT 的更正两处成立、一处部分成立；我原方案两处需要修正。**

### 2.1 `transform: scale()` 是否触发 ResizeObserver

| 主张 | 判断 |
|---|---|
| 我原方案：scale 后 ResizeObserver 会自动触发图表 resize | ❌ **错误** |
| ChatGPT：transform 不改变 layout box，不会触发 | ✅ **正确** |

**核实过程**：`ResizeObserver` 观察的是 layout box（border-box）尺寸；`transform` 只影响绘制（paint）阶段，属于合成层操作，不改变 layout 尺寸。对比之下 CSS `zoom` 会真实改变 layout 尺寸，因此 `zoom` 会触发。

**这个更正的实际影响**：它**不是缺陷，反而是该方案的优点**——ECharts 始终按 1920×1080 的 layout 尺寸渲染，缩放由浏览器统一完成，因此**根本不需要调用 `chart.resize()`**。但需要修正的是**我原方案的表述理由**（原文说"缩放时会触发 resize，无需额外处理"是错的），应改为"缩放不触发 resize，因为 layout 未变，这正是所需行为"。

**继续保留 ResizeObserver**：它仍要负责 Compact/Mobile 模式下**真实布局重排**（三栏→单栏）导致的容器尺寸变化。所以 `useEChart` 一行都不用改，两种模式各自成立。

### 2.2 Tooltip 是否用 `round(hour)`

| 主张 | 判断 |
|---|---|
| 我原方案：formatter 里 `round(hour)` 找原始值 | ⚠️ **有语义错位风险，应修正** |
| ChatGPT：应建立"插值显示层"与"真实数据层"两套 series | ✅ **更稳妥** |

**理由**：鼠标在 x=7.62 时 `round` 得 8，Tooltip 显示 8:00 的值，但鼠标并未落在 8:00。答辩时若被追问"这个点是什么"，会难以解释。

**采纳方案**：显示线 `tooltip:{show:false}`，真实点用低透明度散点层承接 Tooltip。且在答辩语境下，**保留真实节点反而是加分项**——可以讲"曲线是插值得到的，这些节点才是真实采样点"。

### 2.3 `<1500px` media query 是否保留

| 主张 | 判断 |
|---|---|
| 我原方案：保留无害 | ⚠️ **不准确，应清理** |
| ChatGPT：会造成双重适配，应清理 | ✅ **正确** |

**理由**：media query 按**浏览器 viewport** 宽度触发。1920×1080 画布若整体缩放，1366 窗口下会同时发生「内部字体/布局被 media query 改掉」+「整个画布又被 scale 缩放」——两套布局效果叠加，1280 与 1920 下实际是两种排版。

**采纳**：清理现有针对 viewport 宽度的内部 media query，保持单一基准设计。

## 第 3 章 · Batch A：负荷曲线插值（P0，先做）

### 3.1 现状核实

`LoadForecastChart.vue` L54 / L119：`smooth: 0.62` / `smooth: 0.48`，完全依赖 ECharts 内置参数。组长判断准确。

### 3.2 算法选择：Monotone Cubic（PCHIP）而非卷积

| 方案 | 是否改变数据值 | 是否适合画曲线 |
|---|---|---|
| 卷积 / 移动平均 | **会**（100→300→900→300→100 变成 200→500→500） | 适合降噪，不适合绘制 |
| PCHIP 插值 | **不会**（只生成点之间的视觉过渡） | ✅ 适合，且不会过冲 |

**为什么不用普通三次样条**：普通样条在 `100 → 200 → 210 → 150` 这类序列上可能插值出 `100 → 230 → 210`，即制造出原始数据里不存在的假峰值。PCHIP 通过限制导数避免 overshoot。

**与会议措辞的对齐**：组长原话是「卷积**等**算法」。技术上选 PCHIP，但**汇报时要主动说明理由**，并提及"平滑采样 + 可选移动平均"的组合思路。这是沟通问题，不是技术问题。

### 3.3 模块设计

新增 `src/utils/interpolation.js`，**算法层不依赖 Vue / ECharts / 业务 DTO**：

```js
export function pchipInterpolate(points, samplesPerSegment = 12)
export function interpolateSeries(points, options = {})
export function splitContinuousSegments(points)   // 分段，不跨 null
```

`interpolateSeries()` 负责：

- 识别并切分 `null`（不跨空档生成虚假曲线）；
- 每段独立 PCHIP；
- 单点直接保留；两点退化为线性；
- 合并输出 `displayPoints`。

规模：`23 段 × 8 采样 ≈ 185 点`，对 ECharts 无压力。

### 3.4 组件改造

```js
const actualRaw      = hours.map(h => actualMap.get(h)?.chargingEnergy ?? null)
const forecastRaw    = hours.map(h => forecastMap.get(h)?.predictedEnergy ?? null)
const lowerRaw       = hours.map(h => forecastMap.get(h)?.lowerBound ?? null)
const upperRaw       = hours.map(h => forecastMap.get(h)?.upperBound ?? null)

const actualDisplay   = interpolateSeries(actualRaw)
const forecastDisplay = interpolateSeries(forecastRaw)   // 与历史分开插值
```

**三条硬约束**：

1. **历史与实际预测必须分开插值**，不能合并成一条再插——否则算法会跨越「实际 → AI预测」的语义边界。
2. **置信区间不能用 `forecast / lower / upper` 三条各自独立 PCHIP。** 即使原始整点满足 `lower ≤ forecast ≤ upper`，三条线独立插值后中间采样点**理论上仍可能交叉**。应采用**「预测值 + 两侧宽度」结构**：
   ```js
   // 原始整点先算宽度
   lowerGap = forecast - lower
   upperGap = upper - forecast
   // 分别插值
   forecastCurve  = pchip(forecast)
   lowerGapCurve  = pchip(lowerGap)
   upperGapCurve  = pchip(upperGap)
   // 重构，从结构上保证包围关系
   lowGap  = Math.max(0, lowerGapCurve)
   highGap = Math.max(0, upperGapCurve)
   lower   = forecastCurve - lowGap
   upper   = forecastCurve + highGap
   ```
   这样 `lower ≤ forecast ≤ upper` 由数学结构保证，而不是靠最后补救式 clamp。
3. **原始业务点值绝不修改**，Tooltip 显示原始整点。

### 3.5 x 轴改造

插值后产生 `10.125 / 10.250` 这类小数 x，改用数值轴：

```js
xAxis: { type: 'value', min: 0, max: 23 }
```

柱与线同轴，避免为 185 个插值点生成 185 个 category label。

### 3.6 验证脚本

新增 `scripts/verify-interpolation.mjs`，断言数学不变量：

```text
1. 原始节点被曲线精确经过
2. 单调区间不产生额外极值（overshoot 检查）
3. 常量序列仍为常量          [10,10,10,10]
4. 单调序列保持单调          [10,20,30,40] / [40,30,20,10]
5. 尖峰不过冲                [10,100,12,11]
6. null 两侧不被连接         [10,null,30]
7. 无 NaN / Infinity
8. x 严格递增
9. 每个预测采样点 lower ≤ forecast ≤ upper
10. interval width ≥ 0
```

并接入 `package.json` 的 `check` 链路。

### 3.7 chartTheme.js 的最小化决策

`chartTheme.js` **不是必需的**。当前只有 Heatmap 一处使用这组色板，直接定义在 `StationHourHeatmap.vue` 内即可，避免为五个颜色增加一层抽象。**Batch D 按最小改动原则处理**：若届时仍有第二处需要复用，再抽文件。

## 第 4 章 · Batch B：响应式基础设施（P0）

> 📄 **实施方案详见 `docs/v3.6-batch-b-plan.md`**（模块划分、断点反例验算、分步计划、9 项风险应对）。
> 本章保留冻结的设计决策，第 4 章与 Batch B 方案文档如有冲突，以方案文档为准。

### 4.1 方案：Scale Mode + Adaptive Layout Mode 两级

这是本次讨论**最重要的修正**。原方案只有等比缩放，不够——**真正的响应式不能只是把 1920×1080 缩成邮票**。

### 4.2 模式判定

不能只用 `max-width` 判断。反例：

- `1366×768` 宽度小但**比例标准 16:9**，应走 Scale；
- `1024×1366` 宽度不算小但**是竖屏**，必须重排。

因此同时考虑 width / height / aspect：

```js
const ratio = width / height
const targetRatio = 16 / 9
const ratioDiff = Math.abs(ratio - targetRatio) / targetRatio

// 判定（阈值调页面时再定，15% 不是圣经）
ratioDiff <= 0.15            → scale     （等比缩放）
0.15 < ratioDiff <= 0.30     → compact   （两栏/三栏自适应）
ratioDiff > 0.30             → reflow    （纵向排列）
width < 768                  → 强制 reflow
```

### 4.3 Scale Mode 实现

```vue
<div class="viewport-shell">
  <div class="dashboard-canvas" :style="{ transform: `translate(-50%,-50%) scale(${scale})` }">
    <Dashboard />
  </div>
</div>
```

```css
.viewport-shell { width: 100vw; height: 100vh; overflow: hidden; position: relative; }
.dashboard-canvas {
  position: absolute; left: 50%; top: 50%;
  width: 1920px; height: 1080px;
  transform-origin: center center;
}
```

```js
scale = Math.min(viewportWidth / 1920, viewportHeight / 1080)
```

实例：`1600×900 → 0.833`｜`1366×768 → 0.711`｜`2560×1440 → 1.333`

### 4.4 必须同时处理 `global.css`

**关键修正（开工前冻结）**：`overflow:hidden` **不能写死在 `html/body/#app`**，否则与 Reflow 模式的纵向滚动直接冲突。必须改为**模式级控制**。

```css
/* 基础：只解除 viewport 硬限制，不要在这里锁滚动 */
html, body, #app {
  margin: 0;
  width: 100%;
  min-width: 0;     /* 原为 min-width:1280px */
  min-height: 0;    /* 原为 min-height:720px */
}

/* Scale：禁止滚动 */
.viewport-shell[data-layout='scale'] {
  width: 100vw; height: 100vh; overflow: hidden;
}

/* Compact / Reflow：允许纵向滚动 */
.viewport-shell[data-layout='compact'],
.viewport-shell[data-layout='reflow'] {
  width: 100%; min-height: 100vh;
  overflow-x: hidden; overflow-y: auto;
}
```

一句话：**Scale 禁止滚动；Reflow 允许纵向滚动。**

### 4.4.1 Scale 居中实现（简化）

不需要同时处理 `translate` + `scale`，用外层 Flex 居中更简单，也避免 transform 顺序带来的定位问题：

```css
.viewport-shell--scale {
  width: 100vw; height: 100vh;
  display: flex; align-items: center; justify-content: center;
  overflow: hidden;
}
.dashboard-canvas { width: 1920px; height: 1080px; flex: 0 0 auto; transform-origin: center center; }
```
```vue
<div class="dashboard-canvas" :style="{ transform: `scale(${scale})` }">
```

### 4.4.2 Compact Mode 排版（开工前冻结）

原描述"两栏/三栏自适应"过宽，会让实现时自行发挥。冻结为：**核心分析区全宽优先，左/右辅助区再两列排列。**

```text
KPI KPI KPI KPI KPI

┌──────────── 中心重点区域（全宽）────────────┐
│ Load Prediction                              │
│ Heatmap                                      │
└──────────────────────────────────────────────┘

┌──── 左侧分析 ────┬──── 右侧分析 ────┐
│ Platform         │ Top10             │
│ Duration         │ Trend             │
│ Radar            │ Process           │
│                  │ Operations        │
└──────────────────┴───────────────────┘
```

三级结构冻结：

| 模式 | 结构 |
|---|---|
| Scale | 左 \| 中 \| 右（原桌面三栏） |
| Compact | KPI → 中心全宽 →（左/右）两列 |
| Reflow | Header → KPI → 左组三块 → 中组两块 → 右组四块（单列纵向滚动） |

### 4.5 清理旧 media query

删除 `dashboard.css` L217-244 的 `@media (max-width: 1500px)` 整块。理由见 2.3。

### 4.6 Reflow Mode（比例差距大 / 手机）

保留内容层级，改为纵向排列：

```text
Header
KPI ×5          （2 列，最后一个横跨）
订单平台分布
充电时长分布
工作日 vs 周末
充电负荷趋势与 AI 预测
站点 × 时段热力图
站点充电费用 TOP10
充电费用与电量趋势

```

**关键认知**：手机不是"缩小的大屏"，而是同一套数据的纵向 Dashboard。**允许纵向滚动**，不要求一屏塞下全部。

### 4.7 布局状态统一由 composable 管理

新增 `src/composables/useDashboardLayout.js`：

```js
{
  mode: 'scale' | 'compact' | 'reflow',
  scale: 0.833,
  viewportWidth, viewportHeight,
  isCompact, isMobile
}
```

**禁止**十个组件各写 `window.innerWidth < 768`——标准会不一致。组件只接收 props，如 `:compact="isCompact"`。

### 4.8 图表在 Reflow 下的适配（Batch C）

不是"缩小"，而是"重排"：

| 图表 | 桌面 | Reflow |
|---|---|---|
| Heatmap | 24h × 8 站 | `axisLabel.interval` 改为显示 `0,3,6,...,21`；Tooltip 仍保留每小时 |
| Trend | 全月份 | 减少 label 密度（Jan/Mar/May...），数据不减少 |
| 雷达 | 正常 | label 字号下调 |

JS 只负责输出 `mode / scale`，布局交给 CSS（`data-layout` 属性选择器）。

## 第 5 章 · Batch C：Top10 + 右栏

### 5.1 现状核实

`dashboard.css` L117：`grid-template-rows: repeat(10, minmax(0,1fr))` 强制 10 行挤一屏，L124 行高被压到 `minmax(17px, 1fr)`。这是长期压缩字号的根源。

### 5.2 方案

```css
.ranking-list {
  min-height: 0;                    /* 关键：Grid/Flex 子项滚动的必要条件 */
  overflow-y: auto;
  overscroll-behavior: contain;     /* 滚到底不带动整页 */
  display: flex; flex-direction: column;
  gap: 4px;
}
.ranking-row { flex: 0 0 30px; }    /* 固定行高，不再压缩 */
```

**不做自动滚动**：会分散注意力、答辩截图难控、与 hover 冲突。只做手动滚动。

**右栏比例**：不一开始写死精确值，先用温和调整，再按截图微调：

```css
.dashboard-column--right { grid-template-rows: 1fr 1.25fr .85fr .75fr; }
```

目标顺序：Top10 缩、Trend 放、Process / Insights 保持。

**行设计保持单行**，不恢复两行结构。行高释放后，字号可回到更舒展的值。
