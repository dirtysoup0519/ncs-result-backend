## 第 3 章 · 布局状态管理

### 3.1 视口测量的修正（采纳裁决 #2，这是本版最重要的技术修正）

**v1 的错误**：用 `ResizeObserver` 观察 `document.documentElement`，读 `clientWidth/clientHeight`。

**真实缺陷**（比 ChatGPT 描述得更严重）：

```text
Reflow 模式：width=390，内容总高 3000px
  document.documentElement.clientHeight  →  ~3000（内容高，不是视口高）✗
  window.innerHeight                     →  844（视口高）✓

后果：ratio 算成 390/3000 = 0.13 → ratioDiff = 0.93
      但真实 ratio = 390/844 = 0.462 → ratioDiff = 0.74
      两者恰好都落 reflow，看似「没坏」——
      但 1024×1366 这类会因内容撑高而误判，mode 计算整体不可信。
```

**结论**：`html` 的 `clientHeight` 是**内容驱动**的，不满足「视口」语义。
凡是要「视口尺寸」，必须用 `window.innerWidth / innerHeight`。

**修正后的实现**：

```js
function measure() {
  viewportWidth.value = window.innerWidth
  viewportHeight.value = window.innerHeight
}
// 主监听：window resize（rAF 节流，避免地址栏动画期间高频重算）
// 补充监听：visualViewport（存在时），语义最精确
```

**关于 ChatGPT 建议的「简化成 `window.addEventListener('resize')` 就够」**：
方向对，但考虑用户在**答辩场景会切 F11 全屏 / 拖动窗口**，且我已在 v1 论证过首帧闪烁（R5），
所以保留 rAF 节流 + `visualViewport` 兜底（各 3 行代码），不构成过度设计。

### 3.2 首帧正确性（保留 v1 的 R5 修正）

`computed(mode)` 首次求值发生在 `onMounted` **之前**。若初始值为 0 会兜底成 `scale`，
窄屏首帧闪烁一次再跳 `reflow`。

```js
const hasWindow = typeof window !== 'undefined'
const viewportWidth = ref(hasWindow ? window.innerWidth : BREAKPOINTS.designWidth)
const viewportHeight = ref(hasWindow ? window.innerHeight : BREAKPOINTS.designHeight)
```

**setup 阶段同步取初值**，首帧即为正确模式。

### 3.3 断点判定

```js
const BREAKPOINTS = Object.freeze({
  mobileMaxWidth: 768,
  scaleRatioTolerance: 0.15,
  compactRatioTolerance: 0.30,
  designWidth: 1920,
  designHeight: 1080
})

if (w < 768)                 return 'reflow'    // 最高优先
const diff = Math.abs(w / h - 16 / 9) / (16 / 9)
if (diff <= 0.15)            return 'scale'
if (diff <= 0.30)            return 'compact'
                             return 'reflow'
```

**12 个视口样本已验证无反常**（0.15 / 0.30 阈值可用）：

| 视口 | ratioDiff | 模式 |
|---|---|---|
| 1920×1080 / 1600×900 / 1366×768 | 0.000 / 0.000 / 0.001 | scale |
| 1280×800 / 1440×900 | 0.100 | scale |
| 1024×768 | 0.250 | compact |
| 1280×1024 | 0.297 | compact（卡在 0.30 内） |
| 1024×1366 / 768×1024 | 0.578 | reflow |
| 390×844 / 375×667 | 0.740 / 0.684 | reflow |

## 第 4 章 · 三模式布局

### 4.1 Scale

```css
.dashboard-viewport[data-layout='scale'] {
  width: 100vw; height: 100vh;
  display: flex; align-items: center; justify-content: center;
  overflow: hidden;                    /* 禁止滚动 */
}
.dashboard-viewport[data-layout='scale'] .dashboard-canvas {
  width: 1920px; height: 1080px; flex: 0 0 auto;
  transform-origin: center center;
}
```

`scale = Math.min(vw / 1920, vh / 1080)`，**纯 `transform: scale()`**，不用 `translate(-50%,-50%)`
（避免 transform 顺序带来的定位偏差）。

**必须写进代码注释**：Scale 下 `transform` 不改 layout box → `ResizeObserver` 不触发 →
ECharts 始终按 1920×1080 渲染。**这是期望行为，不是 bug**（防止后人误改 `useEChart.js`）。

### 4.2 Compact（采纳裁决 #3，改用 flex）

DOM 确为三个 column（已核实）。改用 **flex** 而非 Grid，因为「中心全宽 + 左右并排」用
`flex-wrap` + `flex-basis` 表达更直观，无需 `order` 与 `grid-column` 配合。

```css
.dashboard-viewport[data-layout='compact'] .dashboard-grid {
  display: flex; flex-wrap: wrap; gap: 10px;
}
/* 中心区：全宽，排第一 */
.dashboard-viewport[data-layout='compact'] .dashboard-column--center {
  flex: 0 0 100%; order: 1;
  display: grid; grid-template-rows: minmax(320px, 1fr) minmax(280px, 1fr);
  gap: 10px;
}
/* 左右：各占一半，排第二 */
.dashboard-viewport[data-layout='compact'] .dashboard-column--left,
.dashboard-viewport[data-layout='compact'] .dashboard-column--right {
  flex: 1 1 calc(50% - 5px); order: 2;
  display: grid; gap: 10px;
}
```

结构（与冻结方案 4.4.2 一致）：

```text
KPI（5 列，窄时 3+2）

┌──────── 中心全宽 ────────┐
│ LoadForecast             │
│ Heatmap                  │
└──────────────────────────┘

┌──── 左 ────┬──── 右 ────┐
│ Platform   │ Top10      │
│ Duration   │ Trend      │
│ Radar      │ Process    │
│            │ Insights   │
└────────────┴────────────┘
```

### 4.3 Reflow（部分采纳裁决 #4）

```css
.dashboard-viewport[data-layout='reflow'] .dashboard-grid {
  display: flex; flex-direction: column; gap: 10px;
}
.dashboard-viewport[data-layout='reflow'] .dashboard-column--center { order: 1; }
.dashboard-viewport[data-layout='reflow'] .dashboard-column--left   { order: 2; }
.dashboard-viewport[data-layout='reflow'] .dashboard-column--right  { order: 3; }
.dashboard-viewport[data-layout='reflow'] .dashboard-column {
  display: flex; flex-direction: column; gap: 10px;
}
```

**顺序裁决（裁决 #4）**：用户补充要求原文是「将原本从左至右排列的三个大块改为上下排列」——
语义是**保持分组**。故：

- **保留**三组结构（中 → 左 → 右）
- **不强行**组内按桌面顺序；若某组内按重要性微调更合理（如右组把 Trend 提到 Top10 前），
  留待 Batch C 视截图决定，**本轮不动组内顺序**

目标顺序：

```text
Header
KPI（2+2+1）
充电负荷趋势与 AI 预测      ← 中心组
站点 × 时段热力图
订单平台分布                ← 左组
充电时长分布
工作日 vs 周末
站点充电费用 TOP10          ← 右组
充电费用与电量趋势
充电过程状态概览
运营建议
```

### 4.4 Reflow 图表高度分档（采纳裁决 #5）

不用统一 320px，按图表空间需求分档：

```css
.dashboard-viewport[data-layout='reflow'] .dashboard-column > * {
  flex: 0 0 auto;                      /* 关键：不能用 height:100% */
}
/* 中心组 */
.dashboard-viewport[data-layout='reflow'] .dashboard-column--center > :nth-child(1) { height: 360px; } /* LoadForecast */
.dashboard-viewport[data-layout='reflow'] .dashboard-column--center > :nth-child(2) { height: 400px; } /* Heatmap */
/* 左组（Platform / Duration / Radar，可互换，量级接近） */
.dashboard-viewport[data-layout='reflow'] .dashboard-column--left   > *              { height: 300px; }
/* 右组（Top10 需行高、Process/Insights 偏文字） */
.dashboard-viewport[data-layout='reflow'] .dashboard-column--right  > :nth-child(1) { height: 420px; } /* Top10 */
.dashboard-viewport[data-layout='reflow'] .dashboard-column--right  > :nth-child(2) { height: 320px; } /* Trend */
.dashboard-viewport[data-layout='reflow'] .dashboard-column--right  > :nth-child(3) { height: 260px; } /* Process */
.dashboard-viewport[data-layout='reflow'] .dashboard-column--right  > :nth-child(4) { height: 260px; } /* Insights */
```

⚠️ **必须显式给高度**：`height:100%` 在无高度约束的 flex 列中会塌缩为 0，
ECharts 直接渲染空白。这是最易踩的坑（R2）。

**实现方式（已裁决）**：用 **CSS `:nth-child` 按列定位**，**不给 `DashboardPanel` 加 `variant` prop**。

| 方案 | 改动文件数 | 边界遵守 | 代价 |
|---|---|---|---|
| **nth-child CSS（选定）** | **1**（`dashboard.css`） | ✅ 完全符合「只改布局、不动组件」 | 耦合 DOM 顺序；顺序变需同步改 CSS |
| `variant` prop | 9（8 个图表 + Panel） | ✗ 需动 8 个组件签名 | 语义更清晰，但超出 Batch B 边界 |

选 **nth-child** 的理由：Batch B 的硬边界是「只做布局、不动图表组件」，
为 8 张图各加一个 prop 属越界；且 CSS 中每档位都带**注释标明对应组件**，
耦合点显式可见。若 Batch C 需要按图表类型而非位置区分，再迁移到 `variant` prop。

### 4.5 KPI（采纳裁决 #8）

```css
/* Scale / Compact：5 列 */
.kpi-strip { display: grid; grid-template-columns: repeat(5, minmax(0, 1fr)); gap: 9px; }

/* Compact 窄：3 + 2 */
.dashboard-viewport[data-layout='compact'] .kpi-strip {
  grid-template-columns: repeat(3, minmax(0, 1fr));
}

/* Reflow：2 + 2 + 1（最后一个全宽） */
.dashboard-viewport[data-layout='reflow'] .kpi-strip {
  grid-template-columns: repeat(2, minmax(0, 1fr)); gap: 8px;
}
.dashboard-viewport[data-layout='reflow'] .kpi-strip > :nth-child(5) {
  grid-column: 1 / -1;                 /* 第 5 个横跨 */
}
```

### 4.6 `global.css` 与 `.dashboard-page`（关键修正）

`overflow:hidden` **不能写死在 `html/body/#app`**，否则与 Reflow 纵向滚动冲突：

```css
/* 基础：解除硬限制，不锁滚动 */
html, body, #app {
  margin: 0; width: 100%;
  min-width: 0;      /* 原 1280px */
  min-height: 0;     /* 原 720px */
}
body { min-height: 100vh; background: var(--bg); }

/* Scale：禁止滚动 */
.dashboard-viewport[data-layout='scale'] { overflow: hidden; }

/* Compact / Reflow：允许纵向滚动 */
.dashboard-viewport[data-layout='compact'],
.dashboard-viewport[data-layout='reflow'] {
  width: 100%; min-height: 100vh;
  overflow-x: hidden; overflow-y: auto;
}
```

`.dashboard-page` 按模式调整：

```css
/* Scale：沿用原值（画布已固定 1920×1080） */
.dashboard-viewport[data-layout='scale'] .dashboard-page {
  height: 100%; min-height: 0; overflow: hidden;
}
/* Compact / Reflow：解除 100vh 锁定 */
.dashboard-viewport[data-layout='compact'] .dashboard-page,
.dashboard-viewport[data-layout='reflow'] .dashboard-page {
  height: auto; min-height: 100vh; overflow: visible;
}
```

### 4.7 删除旧 media query

删 `dashboard.css` L217-244 整块。理由：它按**浏览器 viewport** 宽度触发，
与整体 scale 叠加形成双重适配（1366 下内部字号被改 + 画布又被缩放）。

**副作用说明**：删后 1366 在 Scale 模式下靠 `scale=0.711` 整体缩放，**内部字号不变**。
这是修掉双重适配的必然结果，属期望行为。

### 4.8 选择器优先级

新模式规则统一带 `.dashboard-viewport[data-layout='...']` 前缀（2 层选择器），
特异性高于原有单类选择器，**无需 `!important`**。

## 第 5 章 · 图表组件处理

### 5.1 原则（双方一致，冻结）

```text
Batch B 不修改图表业务逻辑。
响应式只影响：容器尺寸 / label 密度 / 图例布局。
```

### 5.2 ECharts resize 的两模式分工

| 模式 | 是否 resize | 原因 |
|---|---|---|
| Scale | **否** | `transform` 不改 layout box，容器始终 1920×1080，ECharts 认知正确 |
| Compact / Reflow | **是** | 容器宽度真实变化，`ResizeObserver` 触发 `chart.resize()` |

`useEChart.js` **零改动**。

### 5.3 compact prop 的消费范围（已更正）

```vue
<LoadForecastChart  :state="states.loadPrediction"     :compact="narrow" />
<StationHourHeatmap :state="states.stationHourHeatmap" :compact="narrow" />
<FeeEnergyTrend     :state="states.feeEnergyTrend"     :compact="narrow" />
```

三组件已加 `compact: { type: Boolean, default: false }`。

**原表述为「本轮不消费该 prop」——实施中已修正**：窄容器实测暴露出 label 重叠等
可读性缺陷（见 §6.5 的 N4–N6），故 `compact` 的**消费范围限定为**：

```text
允许：坐标轴 label 字号 / 抽稀间隔 / hideOverlap
      legend 字号 / itemGap
      grid 绘图区边距 / 轴名截断宽度
禁止：任何业务数值、单位、格式化函数
      插值逻辑、置信区间结构
      色板、visualMax 分位策略
      四态（loading/empty/unavailable/error）处理
```

即：**只动「画得下画不下」，不动「画的是什么」**。

### 6.1 验收口径修正（采纳 ChatGPT 建议 1）

原写「**1920×1080 与改前逐像素一致**」。工程上加了 `DashboardViewport` 一层后，
DOM 层级、CSS 继承链、transform 层都已变化，**严格逐像素比较意义不大且易陷入无谓争论**。

实际执行的口径为：

```text
视觉一致 —— 三栏宽度/面板位置/图表内容与改前相同
布局尺寸一致 —— 三栏实测宽度 469 / 809 / 596，pageHeight 1080
无功能回归 —— 四态、Tooltip、图例、坐标轴均正常
```

### 6.2 Scale > 1 的验收口径（采纳 ChatGPT 建议 2）

2560×1440 下 `scale = 1.333`，浏览器放大 DOM 必然带来字体抗锯齿、1px 边框变粗、
阴影扩散等**渲染层差异**。这**不是 bug**，验收只要求「比例一致」，不要求与 1920 像素相同。

实测佐证（见 6.4）：Scale 下 ECharts 的 `canvas.width/height` 在各尺寸**恒为 451×182 / 791×390 等设计值**，
只有 CSS 布局盒在随 scale 线性变化 —— 这正是 `transform` 不改 layout box 的预期表现。

## 第 9 章 · 双方意见的最终处置

### 保留（双方一致）

三模式模型、单一状态源、Scale 不改 `useEChart.js`、删旧 media query、
Reflow 允许滚动、不动图表逻辑、1920 为回归基准。

### 采纳的改动

1. `DashboardViewport` 放 `Dashboard.vue` 而非 `App.vue`
2. 视口测量改用 `window.innerWidth/innerHeight`（**修正 v1 实质缺陷**）
3. Compact 改用 **flex** 实现
4. Reflow 保持分组但**不机械**按桌面顺序（组内留待 Batch C）
5. Reflow 图表高度**分档**（非统一 320），用 `:nth-child` CSS 实现（不动组件）
6. 实施步骤合并为 **6 步**，Step 1 验证「页面完全不变」
7. Reflow KPI **2+2+1**（最后一个全宽）

### 舍弃或降级

1. **舍弃**「Grid 的 `order` 支持有限」这一**技术判断**（不准确）——
   但保留其「改用 flex」的结论，理由修正为「更直观」。
   事实：`order` 是 Flex 与 Grid 共用属性，Grid 完全支持。
2. **降级** CSS 变量层（gap / radius）—— 三模式 gap 差异仅 16/12/10，
   直接写在模式选择器里更少一层间接，本轮不做。
3. **不采纳**「简化成裸 `window.addEventListener('resize')`」——
   保留 rAF 节流 + `visualViewport` 兜底（共约 6 行），避免地址栏动画期间高频重算。
4. **不采纳**给 `DashboardPanel` 增加 `variant` prop —— 改用 `:nth-child` CSS。
   理由：Batch B 硬边界是「只做布局、不动组件」，加 prop 会改动 8 个组件的签名与 1 个 Panel，
   共 9 个文件，超出范围。改用 CSS 后**只动 `dashboard.css` 一个文件**（详见 §4.4）。

### 范围冻结

本方案即为 Batch B 最终范围。**不再扩大设计讨论**。
