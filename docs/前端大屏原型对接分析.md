# NCS 前端大屏原型对接分析

> 资料来源：前端同学提供的“新能源汽车充电桩运营分析大屏”截图
> 资料性质：当前视觉原型，可确认组件和展示结构；截图中的数字、单位和文案不能直接作为真实数据或最终指标口径
> 更新时间：2026-09-13

## 1. 原型确认的首屏结构

### 1.1 全局状态区

页面顶部可见：

- 数据日期。
- 订单记录数。
- 站点数。
- 更新时间。

后端统一通过数据状态接口提供这些信息。`dataDate` 表示业务数据日期，`generatedAt` 或 `updatedAt` 表示数据生成/发布时间，两者不得混用。

### 1.2 总览指标卡

原型包含 5 张卡片：

| 组件 | 展示值 | V1 对比信息 |
| --- | --- | --- |
| 总订单数 | 数量 | 不展示 |
| 总充电量 | kWh | 不展示 |
| 总充电费用 | CNY | 不展示 |
| 总用户数 | 数量 | 不展示 |
| 活跃站点数 | 数量 | 不展示 |

截图虽然画出了“较上期变化”，但前端 V1 文档明确建议在比较基准未定义前不接入该字段，因此 V1 只返回当前值。活跃站点定义为统计周期内至少一笔订单，具体统计周期仍需冻结。

### 1.3 左侧分析区

- 订单平台分布：Android、iOS、Web 三类订单数及占比；前端文档明确不应写成“用户来源”。
- 充电时长分布：`0-1h`、`1-2h`、`2-3h`、`3h+` 四个桶，纵轴为订单数。
- 工作日 vs 周末画像：雷达图维度包括订单量、充电量、充电费用、用户数和平均时长。

平台分布的统计对象已由前端 V1 文档明确为订单。环图主值为 `orderCount`，平台费用仅作为可选 tooltip。

### 1.4 中部核心区

“充电负荷趋势与 AI 预测”包含：

- 历史订单数柱状序列。
- 历史充电量实际值曲线，原型标注 MWh。
- AI 预测充电量曲线，原型标注 MWh。
- 历史与预测分界时刻。
- 预测置信区间。
- 按小时查看的粒度入口。

“站点 × 时段热力图”包含：

- 站点纵轴和 00～23 小时横轴。
- 指标选择，当前显示充电量 kWh。
- 日期选择。
- 热力颜色标尺。

热力图要求的数据粒度至少为 `data_date + station_id + stat_hour`，不能由只有“全站小时汇总”的 ADS 表恢复。

### 1.5 右侧分析区

- 站点 Top10：截图写“按充电量排序”，但前端 V1 文档指出现有 Top10 实际按总费用排序；V1 应先按费用并修改页面文案。
- 充电费用与电量趋势：前端 V1 文档要求减少“收益”这一额外业务假设，不返回无来源的服务费。
- 充电过程状态概览：平均 SOC、平均最高温度、平均电压和平均电流，可见“历史统计”和“按站点查看”入口。
- 运营建议：原型底部展示自然语言建议。

“运营建议”不能由查询后端临时拼文案。第一阶段只能采用已登记的规则模板或前端静态文案；若要由数据驱动生成，需要独立规则、触发条件、证据字段和审核责任人。

## 2. 首期组件到接口映射

| 组件代码 | 原型组件 | 建议接口 | 主要数据粒度 | 当前状态 |
| --- | --- | --- | --- | --- |
| `globalStatus` | 数据日期/记录数/站点数/更新时间 | `GET /api/v1/meta/data-status` | 发布批次 | 可实现合同 |
| `overview` | 5 个总览指标卡 | `GET /api/v1/dashboard/overview` | 数据日期/范围 | 待确认口径 |
| `platformDistribution` | 订单平台分布 | `GET /api/v1/audience/platform-distribution` | 日期/平台 | 订单口径已确认 |
| `durationDistribution` | 充电时长分布 | `GET /api/v1/charging/duration-distribution` | 日期/时长桶 | 桶边界由原型初步确认 |
| `weekdayWeekendProfile` | 工作日 vs 周末画像 | `GET /api/v1/charging/weekday-weekend` | 日期范围/日期类型 | 待确认归一化方式 |
| `loadPrediction` | 历史负荷与 AI 预测 | `GET /api/v1/predictions/load` | 小时/实际或预测 | 预测口径阻断 |
| `stationHourHeatmap` | 站点 × 时段热力图 | `GET /api/v1/charging/station-hour-heatmap` | 日期/站点/小时 | 需要站点小时数据 |
| `stationRanking` | 站点 Top10 | `GET /api/v1/stations/ranking` | 日期范围/站点 | V1 默认按总费用 |
| `feeEnergyTrend` | 费用与电量趋势 | `GET /api/v1/revenue/trend` | 月/费用和电量 | 不返回服务费 |
| `processSummary` | 充电过程状态概览 | `GET /api/v1/charging/process-summary` | 日期/站点可选 | 站点级来源待确认 |
| `operationSuggestions` | 运营建议 | 前端本地模板；后端接口预留 | 建议生成批次 | P3，不阻塞 V1 |

原型未出现站点地图、站点详情页、电桩状态分布和用户画像详情。相关接口继续保留为扩展能力，但不作为当前首屏 P0 联调条件。

## 3. 后端响应设计要求

### 3.1 总览卡

每张卡返回稳定指标代码、展示名称、当前值、单位和精度。V1 不返回对比值、对比比例或对比基准；未来启用时必须先冻结比较周期，前端不得自行推断“上期”。

### 3.2 历史与预测组合图

接口必须区分：

- `actualOrderCount`：历史订单数。
- `actualChargingEnergy`：历史充电量。
- `predictedChargingEnergy`：预测充电量。
- `lowerBound`、`upperBound`：预测区间；模型不支持时明确为空。
- `forecastStartAt`：历史与预测分界。
- `modelVersion`、`predictionRunId`、`generatedAt`。

实际和预测序列必须使用相同时间轴及明确单位。原型同时使用 kWh、MWh，后端返回数值时必须随字段返回单位，不能让前端猜测换算。

### 3.3 雷达图

工作日/周末雷达图涉及不同量纲，接口同时返回原始值和归一化值。归一化算法由指标合同登记，前端只使用 `normalizedValue` 绘图，悬浮提示显示原始值与单位。

### 3.4 热力图

返回固定 0～23 小时、站点稳定 ID/名称、值和 `isObserved`。没有观测的数据槽可以补零，但必须与真实零值区分。

### 3.5 过程状态

SOC 使用 `[0,1]` 或百分比必须统一；温度、电压、电流分别携带 `°C`、`V`、`A`。是否按全站、单站或时间窗口聚合必须在响应元数据中给出。

## 4. 根据原型新增或调整的优先级

按前端 V1 对接文档调整开发顺序：

- P0：数据概况、KPI、订单平台分布、站点 Top10、费用与电量趋势、过程状态概览。
- P1：充电时长分布、工作日/周末画像、站点小时热力图。
- P2：负荷预测。
- P3：运营建议，V1 可由前端固定规则生成。

站点地图、站点详情、电桩状态分布继续作为后续页面能力，不阻塞当前首屏。

## 5. 需要前端/产品确认

1. 顶部“订单记录”与总览“总订单数”为什么不同，各自统计范围是什么。
2. 未来是否启用“较上期”；如果启用，再确认上一日、上一月、上一相同长度窗口或同比。
3. 平台总费用是否需要用于 tooltip；订单占比由后端返回还是前端计算，双方只能选一个口径来源。
4. 工作日/周末雷达图使用原始值加 `max`，还是同时返回归一化值。
5. 预测目标是否为充电量，原型中的订单柱状数据是否仅为历史辅助序列。
6. `cutoffHour` 的来源和预测范围；预测置信区间是否可提供。
7. 负电流是否表示充电方向；`avgMaxTemperature` 的展示名称；是否支持站点筛选。
8. 页面加载一次还是按发布版本低频刷新；断网、组件错误和数据过期如何展示。
9. 原型目标分辨率及缩放策略；这些影响前端，不改变数据接口合同。

接口冻结稿已内部确定：热力图默认 `metric=kwh`、Top 8、最大 10；费用与电量趋势默认按月。这两项不再阻断后端实现，如前端提出变更则按合同变更流程处理。

## 6. 数据真实性边界

截图中展示的订单数、充电量、费用、用户数、站点数、趋势点和过程状态值均视为演示数据。除非数仓提供可复核数据和指标口径，否则不得写入数据库种子、接口默认响应、模型训练样例或验收预期。
