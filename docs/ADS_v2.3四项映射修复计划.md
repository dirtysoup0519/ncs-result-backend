# ADS v2.3 四项映射修复计划

> **历史留档（2026-09-15）**：v2.3 专项已退役，当前只验收 v2.5。本文中的版本、数据量和修复步骤不得作为当前操作指令。

> 状态：历史留档（2026-09-15）。按最新数据口径，项目只使用 ADS v2.5 交付，v2.3 不再单独适配；本计划中仍适用的修复（数据状态稳定性、排行跨期聚合、热力图跨期聚合）已在后续提交中实现。

## 1. 结论与范围

ADS v2.3 的 10 个数据集已完整导入结果库，文件校验和、主键和行数检查通过。概览、平台分布、时长分布、工作日/周末画像和费用电量趋势已经与原始 CSV 对齐。本计划只修复以下四项查询口径，不修改上游 ADS 文件，不修改前端源码，也不引入机器学习逻辑：

1. 顶部数据状态的订单记录数不稳定。
2. 站点排行错误地只保留最后业务日有订单的站点。
3. 站点小时热力图错误地只读取最后业务日。
4. 充电过程概览读取最后一天，而不是全周期历史聚合。

冻结 API 路径和 JSON 字段保持不变，前端不需要改接口。

## 2. 原始数据基线

统计周期为 `2014-01-24` 至 `2015-12-28`，上游声明 `FULL_SNAPSHOT`。

| 数据集 | 原始行数 | 关键核对结果 |
| --- | ---: | --- |
| `dashboard_overview` | 1 | 订单 5,000；电量 36,200.98 kWh；费用 1,072.49 元 |
| `station_daily` | 3,834 | 合计订单、电量、费用与总览一致；104 个活跃站点 |
| `station_reference` | 105 | 105 个登记站点 |
| `station_hour_daily` | 4,840 | 合计订单、电量、费用与总览一致；104 个站点 |

其中 `299`、`341`、`3,834` 等是各 ADS 文件的物理行数，不能直接作为顶部“订单记录”。

## 3. R1：数据状态确定化

### 当前问题

`api_v1_data_status` 每个已发布数据集返回一行，而查询在相同 `data_date` 下没有稳定的次级排序。默认请求可能随机取到 `process_daily.row_count=299`、`station_daily.row_count=3834` 等值。

### 目标逻辑

- 默认数据状态以当前发布的 `dashboard_overview` 为业务锚点。
- `sourceRecordCount` 映射到 `total_order_count`，当前值为 `5000`。这是因为 ADS v2.3 没有提供独立的“订单源记录数”，前端字段明确显示为“订单记录”。
- `stationCount` 映射到 `station_count=105`；不得用 `active_station_count=104` 代替。
- `dataDate` 使用统计周期结束日期 `2015-12-28`。
- `updatedAt` 使用对应发布批次的更新时间。
- 带 `datasetCode` 的内部诊断查询仍可返回指定数据集的物理行数，但不得影响无参数的首屏状态。

### 实现位置

- 调整 `api_v1_data_status` 视图或新增稳定的首屏状态分支。
- 调整 `DbApiDashboardRepository._fetch_data_status`，明确默认数据集，禁止无排序的同日期竞争。

### 验收

- 连续请求 100 次结果一致。
- 默认返回订单记录 5,000、覆盖站点 105。
- 指定 `datasetCode` 时返回值可追溯到相应导入批次。

## 4. R2：全周期站点 TOP10

### 当前问题

视图先按站点聚合全周期数据，却给每个站点附加各自最后活跃日期；仓储随后按全局最大日期过滤，最终只保留最后一天有订单的站点。

### 目标逻辑

- 在当前发布的 `station_daily` 批次内按 `station_id` 聚合全统计周期。
- `order_count`、`total_kwh`、`total_fees` 使用 `SUM`。
- 所有站点统一使用该发布批次的最大 `data_date` 作为响应元数据日期。
- 默认按 `total_fees DESC, station_id ASC` 排序并限制 10 条。
- 当前原数据的第一名应为站点 `369001`，费用 `123.66` 元、订单 `478`、电量 `3427.77` kWh。

### 实现位置

- 重建 SQLite/MySQL 的 `api_v1_station_ranking` 视图。
- 结果库 schema 版本递增，保证既有数据库执行迁移后重建视图。

### 验收

- 返回 10 个不同站点。
- 排名连续，从 1 开始。
- 第一名及其三项数值与 ADS CSV 一致。
- TOP10 结果与直接聚合 `station_daily.csv` 的结果逐项一致。

## 5. R3：全周期站点小时热力图

### 当前问题

当前默认查询只读取最大 `data_date`。原数据在 `2015-12-28` 只有一个站点的一条小时记录，因此界面只显示 `Top 1` 和一个有效色块。

### 目标逻辑

- 在当前发布的 `station_hour_daily` 批次内，按 `station_id + stat_hour` 聚合全统计周期。
- `orders`、`kwh`、`fees` 分别使用对应字段求和。
- 站点选择按所请求指标的全周期合计值降序，而不是按单个小时峰值选择。
- 默认选择前 8 个站点，最多 10 个。
- 每个站点返回 0 至 23 时；缺失组合补零并标记 `isObserved=false`。
- `valueRange` 必须覆盖补零值和真实值。

### 实现位置

- 重建 `api_v1_station_hour_heatmap` 的 v2.3 分支为全周期聚合视图。
- 调整仓储的站点选择查询，先计算站点总量，再读取选中站点的小时矩阵。

### 验收

- 默认返回 8 个站点和 192 个点。
- 每个站点恰好 24 个小时，不重复、不缺小时。
- 各站点 24 小时之和等于其 ADS 全周期合计值。
- 三种指标 `kwh/orders/fees` 的单位和 JSON 数值类型符合冻结合同。

## 6. R4：全周期充电过程聚合

### 当前问题

接口按日期倒序只取一行，因此当前展示的是 `2015-12-28` 当日一条过程记录，不符合“全站历史过程聚合”的界面语义。

### 目标逻辑

- `recordCount` 和 `sessionCount` 对全周期求和。
- 日均值必须按 `record_count` 加权，禁止直接对每日平均值再次做简单平均。
- SOC 在结果库保持上游百分数口径，在 API 边界转换为 `0..1` 比率。
- 当前数据的预期历史聚合约为：记录 2,328、会话 2,328、SOC 45.06%、电流 -23.93 A、电压 337.60 V、峰值温度 35.28℃。
- 继续只支持 `ALL_STATIONS`，不伪造站点级过程数据。

### 实现位置

- 重建 `api_v1_process_summary` 的 v2.3 分支，使用加权聚合。
- 保持 `/api/v1/charging/process-summary` 响应字段不变。

### 验收

- 计数和加权指标与直接计算 `process_daily.csv` 的结果一致。
- 负电流方向保持不变。
- API 中 SOC 为比率，前端显示为百分数。
