# NCS 大屏接口冻结合同 V1

> 合同版本：`1.0-rc1`
> 冻结日期：2026-09-13
> 最后更新：2026-09-15（变更明细见第 12 节）
> 适用方：Vue 3 / DataV 前端大屏、查询后端、结果库；预测接口仅在未来存在已处理预测结果时启用
> 状态：内部冻结基线；主要 DTO、视图映射和查询路由已实现并通过 ADS v2.1/MySQL 冒烟验证
> 字段示例：见 `前端接口协议.md`

> 当前部署结构见 `项目业务架构与代码规划.md`；运行位置变化不改变本接口合同。

## 1. 冻结结论

V1 冻结的是接口边界，不是演示数字。以下内容冻结后不得在联调期间直接改名或改类型：

- HTTP 方法和正式路径。
- 请求参数名称、类型和默认行为。
- JSON 外层结构、字段命名和数值序列化规则。
- 基础单位、枚举、排序、空数据和错误行为。
- 历史数据、预测数据和系统时间的语义边界。

尚未取得真实数据或算法结论的组件保留相同结构，通过 `availability=UNAVAILABLE`、空集合或可选字段 `null` 降级，不以临时字段、假数据或 ECharts 配置替代。

## 4. 通信与类型合同

### 4.1 基本规则

| 项目 | 冻结值 |
| --- | --- |
| 传输 | HTTP/HTTPS + UTF-8 JSON |
| API 前缀 | `/api/v1` |
| 字段命名 | `camelCase` |
| 业务日期 | `YYYY-MM-DD`，按 `Asia/Shanghai` 解释 |
| 时间戳 | ISO 8601，必须包含时区 |
| 计数 | JSON integer |
| 金额、比例、能量及其他连续值 | JSON decimal string |
| 比例范围 | `[0,1]` |
| 金额基础单位 | `CNY` |
| 充电量基础单位 | `kWh` |
| 时长基础单位 | `hour` 或明确的分钟边界 |
| 前端展示换算 | 万元、MWh、百分比由前端 API 层换算 |

后端只返回业务数据和元数据，不返回 ECharts `option`、颜色、坐标位置或页面布局。

### 4.2 成功响应

```json
{
  "code": "OK",
  "message": "ok",
  "data": {},
  "meta": {
    "requestId": "request-id",
    "dataVersion": "dataset:batch-id",
    "dataDate": "2019-09-13",
    "generatedAt": "2026-09-13T14:00:00+08:00",
    "staleness": "FRESH",
    "empty": false,
    "partial": false
  }
}
```

`requestId`、`generatedAt`、`staleness`、`empty` 和 `partial` 必须返回。没有适用业务日期或数据版本时，对应字段返回 `null`，不得省略。

前端 Mock 中的数字 `code: 0` 不进入正式合同。V1 成功码固定为字符串 `OK`，错误码也固定为字符串。

### 4.3 错误响应

```json
{
  "code": "VALIDATION_INVALID_PARAMETER",
  "message": "date range is invalid",
  "data": null,
  "errors": [
    {"field": "startDate", "reason": "must not be after endDate"}
  ],
  "meta": {"requestId": "request-id"}
}
```

| HTTP | 场景 | 行为 |
| ---: | --- | --- |
| 200 | 正常或合法空数据 | `code=OK`；空数据设置 `meta.empty=true` |
| 200 | 已知条件能力未启用 | `code=OK`；条件组件的 `data.availability=UNAVAILABLE` |
| 400 | 参数或枚举非法 | `VALIDATION_*`，前端不得自动重试 |
| 401/403 | 未认证或无权限 | `AUTH_*` |
| 404 | 未知路径 | `QUERY_ROUTE_NOT_FOUND`，表示版本或路由不匹配 |
| 503 | 数据库或依赖暂不可用 | `DEPENDENCY_*`，前端保留最后成功数据并退避重试 |
| 500 | 未分类服务错误 | `INTERNAL_*`，必须提供 `requestId` |

单组件失败不得阻断其他组件。禁止以 HTTP 200 + 假业务数字掩盖错误。

条件组件不可用时仍保持字段结构：`availability` 返回 `UNAVAILABLE`，数组返回 `[]`，没有值的标量返回 `null`，已知的指标代码和单位照常返回。前端不得把不可用状态等同于业务值为零。

## 5. 通用查询行为

| 参数 | 类型 | 默认与限制 |
| --- | --- | --- |
| `dataDate` | date | 缺省读取最新已发布日期 |
| `startDate`、`endDate` | date | 成对使用，与 `dataDate` 互斥；最大跨度由能力元数据返回 |
| `regionId` | string | 稳定业务 ID，不接收名称代替 |
| `stationId` | string | 稳定业务 ID；仅能力支持时可用 |
| `metric` | enum | 只接受接口登记的白名单值 |
| `granularity` | enum | `HOUR`、`DAY`、`MONTH` |
| `limit` | integer | 必须为正整数，接口分别设最大值 |

同一请求的所有组件必须读取已发布批次，不能读取 staging 或半发布数据。数据库查询账号只能访问 `api_v1_*` 视图。

## 6. 字段级冻结清单

### 6.1 数据状态

`GET /api/v1/meta/data-status`

| 字段 | 类型 | 必填 | 语义 |
| --- | --- | --- | --- |
| `dataDate` | date | 是 | 业务数据日期 |
| `sourceRecordCount` | integer | 是 | 顶部“订单记录”；不与总订单数合并 |
| `stationCount` | integer | 是 | 数据范围内站点数 |
| `updatedAt` | datetime | 是 | 数据集生成/发布时间，不是设备实时采集时间 |
| `qualityStatus` | enum | 是 | `PASSED`、`WARNING`、`FAILED`、`UNKNOWN` |
| `staleness` | enum | 是 | `FRESH`、`STALE`、`UNKNOWN` |

### 6.2 总览指标

`GET /api/v1/dashboard/overview`

响应固定为 `data.items[]`，每项包含：`metricCode`、`displayName`、`value`、`unit`、`precision`。首批指标代码固定为：

- `total_order_count`
- `total_charging_energy`
- `total_charging_fee`
- `total_user_count`
- `active_station_count`

V1 不定义 `comparisonValue`、`comparisonRatio` 或 `comparisonBasis`。活跃站点按“统计周期内至少一笔订单”计算，统计周期跟随本次请求的数据范围。

### 6.3 订单平台分布

`GET /api/v1/audience/platform-distribution`

响应包含 `subject=ORDER`、`totalOrderCount`、`unit=count` 和 `items[]`。每项固定包含 `platformCode`、`displayName`、`orderCount`、`orderRatio`；`totalFees` 为可空字段。首批平台枚举：`ANDROID`、`IOS`、`WEB`、`UNKNOWN`。

`orderRatio` 由后端按同一响应中的 `totalOrderCount` 计算，前端不重复计算业务占比。

当分母为 0 时返回空列表并设置 `meta.empty=true`，不得通过除零生成 `null`、`NaN` 或无穷值。

### 6.4 充电时长分布

`GET /api/v1/charging/duration-distribution`

响应包含 `subject=ORDER`、`unit=count` 和 `items[]`。每项包含 `bucketCode`、`label`、`lowerMinutes`、`upperMinutes`、`orderCount`、`ratio`。

分桶边界冻结为左闭右开：`[0,60)`、`[60,120)`、`[120,180)`、`[180,+∞)`，代码依次为 `PT0H_PT1H`、`PT1H_PT2H`、`PT2H_PT3H`、`PT3H_PLUS`。

### 6.5 工作日/周末画像

`GET /api/v1/charging/weekday-weekend`

响应包含 `indicators[]`、`series[]`、`normalization`。指标固定顺序为订单量、充电量、费用、用户数、平均时长。`series.dayType` 固定为 `WEEKDAY` 或 `WEEKEND`；`rawValues` 的长度和顺序必须与 `indicators` 一致。

`indicators.max`、`series.normalizedValues` 和 `normalization` 属于同一可选能力：算法未登记时全部返回 `null`；启用后必须成组返回，并带 `method` 和 `version`。原始值始终必填。

### 6.6 站点小时热力图

`GET /api/v1/charging/station-hour-heatmap`

`metric` 允许 `kwh`、`orders`、`fees`；默认 `kwh`。`limit` 默认 8、最大 10。响应固定包含 `availability`、`metricCode`、`unit`、0～23 的完整 `hours`、`stations[]`、`points[]` 和 `valueRange`。

每个点包含 `stationId`、`hour`、`value`、`isObserved`。缺失槽位可以补零，但必须设置 `isObserved=false`，真实零值设置为 `true`。默认站点集合按所选指标降序、`stationId` 升序确定。

### 6.7 站点 Top10

`GET /api/v1/stations/ranking`

V1 固定 `metric=fees`，`limit` 默认且最大为 10。响应包含 `metricCode=total_fees`、`unit=CNY` 和 `items[]`；每项包含 `rank`、`stationId`、`stationName`、`orderCount`、`totalFees`、`totalKwh`、`value`。

排序固定为 `totalFees DESC, stationId ASC`，`rank` 从 1 连续编号。默认读取最新已发布业务日期；跨日查询必须显式提交 `startDate` 和 `endDate`。前端标题必须改为“按充电费用排序”。

### 6.8 充电费用与电量趋势

`GET /api/v1/revenue/trend`

默认 `granularity=MONTH`。响应包含 `granularity`、`points[]` 和 `units`；每个点包含 `period`、`orderCount`、`totalFees`、`totalKwh`。基础单位固定为 CNY 和 kWh。

V1 不返回 `serviceFee`、利润、成本或“收益”。前端可换算为万元和 MWh，但不得改变 tooltip 中的单位含义。

### 6.9 充电过程历史聚合

`GET /api/v1/charging/process-summary`

响应包含 `scope`、`recordCount`、`sessionCount` 和 `metrics[]`。指标代码固定为：

- `average_soc`，单位 `ratio`
- `average_current`，单位 `A`
- `average_voltage`，单位 `V`
- `average_max_temperature`，单位 `celsius`

负电流保留方向语义，前端不得取绝对值。`average_max_temperature` 表示“最高温度字段的平均值”，不得展示成普通平均温度。没有站点级数据时，`stationId` 参数返回 `400 VALIDATION_UNSUPPORTED_FILTER`，全站聚合仍可用。

### 6.10 历史负荷与预测

`GET /api/v1/predictions/load`

请求参数：

| 参数 | 类型 | 必填 | 默认与限制 |
| --- | --- | --- | --- |
| `date` | date | 否 | 与 `cutoffHour` **成对使用**：同时给出时定位一个已发布批次；同时省略时由后端解析最新已发布运行并回显 |
| `cutoffHour` | integer | 否 | `0–23`；只给其中之一返回 `400 VALIDATION_INVALID_PARAMETER` |
| `horizon` | enum | 否 | `1h`、`6h`、`24h`；其余值返回 `400 PREDICTION_UNSUPPORTED_HORIZON` |
| `stationId`、`regionId` | string | 否 | 合同登记但当前数据源无站点/区域维度，传入返回 `400 VALIDATION_UNSUPPORTED_FILTER`（见第 8 节） |

响应包含 `availability`、`date`、`cutoffHour`、`forecastStartAt`、`energyUnit=kWh`、`orderCountUnit=count`、`actual[]`、`forecast[]`、`interval`、`modelVersion`、`predictionRunId`、`generatedAt`。

`date`、`cutoffHour`、`forecastStartAt`、`modelVersion`、`predictionRunId` 回显的是**实际解析出的批次**，不是请求字面量；省略参数的调用同样必须拿到具体值。本接口的 `meta.dataDate` 取该批次的业务日期，与 `data.date` 一致。

`actual[].hour` 与 `forecast[].hour` 都是从业务日期 0 点起的连续小时偏移；`forecast[].hour >= 24` 表示次日（`24` = 次日 0 点），上限为 `cutoffHour + 24`，即不超过 `47`。预测从 cutoff **之后一小时**开始（`forecastStartAt = cutoff 时刻 + 1h`），截止小时本身既不属于 `actual` 也不属于 `forecast`。完整规则见 `预测接口hour跨天扩展说明.md`。

`actual` 只允许出现截止时刻以前的观测；`forecast` 从 `forecastStartAt` 开始。线上响应禁止混入截止点之后的未来实际值，回测使用独立接口或离线报告。预测区间不可用时，`interval.available=false`，`lowerBound`、`upperBound` 和 `confidenceLevel` 返回 `null`。

预测目标、模型阈值和正式截止点来源未确认前，该接口返回 `availability=UNAVAILABLE` 和空序列，禁止返回演示曲线。

## 7. 能力发现与前端调用顺序

页面启动按顺序调用：

1. `GET /api/v1/meta/capabilities`
2. `GET /api/v1/meta/filter-options?topic={topic}`
3. `GET /api/v1/dashboard/manifest`
4. 并行调用 manifest 中 `available=true` 的组件接口

`capabilities` 每项返回 `capabilityCode`、`registered`、`available`、`endpoint` 和 `priority`；`manifest` 每项返回 `componentCode`、`registered`、`available`、`endpoint`、`priority` 和 `refreshIntervalSeconds`。`registered=true` 只表示路由已注册，`available=true` 才表示对应数据源已有可用发布批次。两者都不返回布局，前端负责布局和 ECharts 配置，后端负责业务口径、排序、补点、发布版本和质量状态。

## 8. 仍需对接但不改变结构的事项

| 事项 | 对接方 | 未确认时的固定降级 |
| --- | --- | --- |
| “订单记录”与“总订单数”的统计范围 | 数仓/产品 | 保持两个字段独立 |
| 平台费用是否有真实来源 | 数仓 | `totalFees=null` |
| 雷达归一化规则 | 产品/数仓 | 可选归一化字段全部为 `null` |
| 站点小时数据 | 数仓 | 热力图 `availability=UNAVAILABLE` |
| 过程指标站点粒度 | 数仓 | 只支持全站范围 |
| 预测的站点/区域粒度 | 数仓/算法 | `rpt_load_prediction` 无站点、区域维度，`stationId`、`regionId` 返回 `400 VALIDATION_UNSUPPORTED_FILTER`；全站聚合曲线照常可用 |
| 预测目标、截止点和区间 | 算法/产品/数仓 | 预测接口不可用 |
| 数据刷新周期 | 数仓/部署 | manifest 使用保守刷新建议并显示真实更新时间 |
| 鉴权、跨域和域名 | 部署/项目负责人 | 仅可信测试网络联调 |

这些事项关闭时只允许启用能力或填充已冻结的可选字段，不能静默修改字段名、类型、单位或既有语义。

## 9. 变更控制

- 新增不影响既有语义的可选字段：记录变更，保持 `/api/v1`。
- 新增枚举：前端必须按 `UNKNOWN` 兜底，发布变更说明。
- 删除字段、改字段类型、改单位、改分桶或改指标语义：必须发布新 API 版本。
- 更换上游表名、导入方式或数据库实现：只修改适配器和视图映射，不修改本合同。
- OpenAPI、DTO、数据库视图与本文不一致时，以评审后的合同版本为准，修复前不得宣称完成联调。

## 10. 冻结后的实现顺序

1. 根据本文生成请求/响应 DTO 和 OpenAPI。
2. 建立 `API 字段 -> api_v1_* 视图列 -> rpt_* 列 -> 上游字段` 追踪表。
3. 先实现 P0 的 Mock 仓储和合同测试，再接真实 MySQL 视图。
4. 按 P0、P1、P2 波次联调；单个数据能力缺失不阻塞其他组件。
5. 对接方书面确认后，将版本从 `1.0-rc1` 提升为 `1.0`，只修改确认状态，不改已冻结结构。

## 11. 对外确认清单

前端确认：

- 使用正式领域路径和字符串成功码 `OK`。
- 接受 decimal string，在 API 封装层统一转换与展示换算。
- V1 不显示环比；Top10 文案改为按充电费用排序。
- 组件只消费业务数据，不要求后端返回 ECharts 配置。

数仓确认：

- 为每个冻结字段提供上游列或计算口径。
- 确认订单记录、总订单、用户、活跃站点和过程指标的统计范围。
- 确认平台费用、站点小时粒度和站点级过程数据是否可用。

算法确认：

- 明确预测目标、训练与推理粒度、`cutoffHour` 来源、预测范围和验收阈值。
- 明确是否提供预测区间及置信水平。

任一方未确认的事项按第 8 节降级，不反向修改已冻结结构。
