# NCS 结果库与后端内部逻辑及对接设计

> 状态：历史总体设计；结果库、管理后端和查询后端的核心部分已落地，机器学习章节仅作未来参考
> 当前进度：见 `项目当前状态与下一步.md`
> 范围：Hive ADS、机器学习训练/预测、MySQL 结果库、数据库管理服务、查询后端及 Web 大屏投射

> **当前范围覆盖说明（2026-09-15）**：机器学习训练、调参和评估仍不属于本仓库；外部模型登记、受控推理和预测发布已恢复为当前实现。本文中训练流水线仍是未来备选，推理输入/输出和发布边界以 `ADS_v2.5自动同步与模型推理设计.md` 为准。

> **当前结构覆盖说明**：MySQL 固定在虚拟机，数据管理程序支持 Windows 远程输入和虚拟机就地处理，查询 API 运行在 Windows。当前结构和代码阶段以 `项目业务架构与代码规划.md` 为准。

## 1. 结论与核心决策

当前系统拆成三个独立部分：

1. **结果库 `ncs_analytics`**：运行在虚拟机，保存已发布的 ADS 统计结果并提供版本化视图。
2. **数据库管理服务 `data-admin-service`**：可运行在 Windows 或虚拟机，负责读取交接数据、校验、导入、发布、回滚和审计。
3. **查询后端 `analytics-query-api`**：运行在 Windows，只通过虚拟机 IP 读取稳定视图并向大屏提供 REST API。

模型训练流水线不属于当前系统；模型加载、推理和预测结果发布属于当前系统，本文后续训练章节仍作为未来备选保留。

关键约束：

- 浏览器前端不得直连 MySQL；“用视图给前端”落地为：**查询后端使用只读账号查询数据库视图，再把结果通过 API 返回前端**。
- 查询后端只依赖 `api_v1_*` 视图，不依赖 ADS 表名、导入临时表或底层结果表结构。
- 数据库管理服务与查询后端分开部署、分开授权，避免管理权限进入面向前端的进程。
- 视图承担稳定数据契约和字段适配，不承担重计算。复杂聚合在 Hive ADS 或结果表中完成。
- MySQL 没有原生物化视图；性能不足时建设预聚合结果表，不用普通视图重复扫描大量明细。
- Qt 阶段已经完成，Qt 用户端、Qt 管理端、交易业务库和设备控制不再作为本阶段的设计对象，也不预留兼容接口。
- 机器学习是当前阶段的核心能力之一，但与查询 API 解耦：大屏查询已发布的离线预测结果，不在请求链路中实时训练或推理。
- 模型训练失败或新预测未通过校验时，基础统计大屏继续读取上一可用数据，不被机器学习流水线阻塞。

资料确认的可视化主题包括：

- 未来 1h/6h/24h 负荷、空闲桩数量和高峰时段预测；资料将其列为可选，但根据当前分工，本设计将负荷预测纳入核心范围。

1. 项目说明书中的数据库端偏向交易业务库，包含用户、站点、电桩、订单、管理员等实体；数仓课件中的 MySQL 是 ADS 下游结果库。本仓库只负责后者。
2. 项目说明书提到 Qt/C++、SQLite、Socket，但该阶段已经完成。本设计不延续 Qt 架构，只采用 Flask/MySQL、机器学习离线任务和 Vue/ECharts 大屏链路。

## 3. 项目边界

### 3.1 本仓库负责

- 接收 Hive ADS 发布的数据集或导出文件。
- 使用 ADS 特征数据完成模型训练、评估和离线预测。
- 管理模型版本、训练运行、预测运行及预测结果发布状态。
- 管理 MySQL 分析结果表、视图和控制表。
- 管理导入批次、质量校验、数据发布和回滚。
- 向 Vue/ECharts 大屏提供只读查询 API。
- 提供数据日期、批次状态、数据质量摘要和服务健康信息。
- 维护“前端组件 -> API -> 视图 -> 结果表 -> ADS/预测数据集 -> 模型版本”的可追溯关系。

### 3.2 本仓库不负责

- ODS、DWD、DWS、ADS 的生产加工逻辑。
- 已完成的 Qt 用户端、Qt 管理端及其 Socket 通信。
- 用户注册登录、钱包充值、预约、计费、订单结算、设备控制等交易业务。
- 腾讯地图、短信、支付、天气等第三方服务的业务封装。
- 大屏视觉稿、ECharts 组件和投屏页面的具体前端实现。
- Hadoop/Hive/MySQL 生产环境安装和调度平台运维。

### 3.3 当前机器学习范围

基础机器学习目标为充电负荷预测，支持站点级未来 1h、6h、24h 的预测结果。内部设计同时预留模型评估、模型版本、预测批次和模型切换能力。

```text
ADS 特征数据 -> 训练 -> 评估 -> 模型登记/启用
已启用模型 + 最新特征 -> 离线预测 -> 质量校验 -> 结果库发布 -> 大屏查询
```

故障诊断、需求调度、智能风控、电池健康预测等能力只有在明确标签、特征和验收指标后再增加，不与负荷预测共用含糊的“万能模型”接口。

## 4. 总体架构

```text
                         上游数仓边界
┌─────────────────────────────────────────────────────────┐
│ Hive ADS 统计数据集 + 机器学习特征数据集                 │
│ schema_version + data_date + grain + row_count           │
└──────────────────┬───────────────────────────┬──────────┘
                   │                           │
                   │ 统计结果                  │ 特征数据
                   │                           ▼
                   │              ┌────────────────────────┐
                   │              │ ml-pipeline            │
                   │              │ 训练 -> 评估 -> 离线预测│
                   │              └───────────┬────────────┘
                   │                          │ 模型/预测 manifest
                   ▼                          ▼
┌─────────────────────────────────────────────────────────┐
│ data-admin-service（内部管理面）                         │
│ 导入 -> staging -> 数据/预测质量校验 -> 发布/回滚        │
└──────────────────────────┬──────────────────────────────┘
                           │ 管理权限、批次状态和审计
                           ▼
┌─────────────────────────────────────────────────────────┐
│ MySQL: ncs_analytics                                     │
│ ctl_* 控制表 | ml_* 模型元数据 | stg_* 临时表            │
│ rpt_* 统计/预测结果表 | api_v1_* 稳定视图                │
└──────────────────────────┬──────────────────────────────┘
                           │ 仅 SELECT 视图
                           ▼
┌─────────────────────────────────────────────────────────┐
│ analytics-query-api（大屏查询面）                        │
│ 参数校验 -> 用例服务 -> 视图仓储 -> DTO -> REST API      │
└──────────────────────────┬──────────────────────────────┘
                           │ HTTP/JSON
                           ▼
                 Vue + ECharts -> 浏览器全屏投射
```

机器学习、管理面和查询面必须解耦：

| 项目 | `ml-pipeline` | `data-admin-service` | `analytics-query-api` |
| --- | --- | --- | --- |
| 使用者 | 内部算法开发/调度器 | 内部开发/运维 | Web 大屏 |
| 主要职责 | 训练、评估、离线预测 | 导入、校验、发布、回滚 | 查询、组装、稳定输出 |
| 数据库权限 | 通过管理接口登记结果；不直写发布表 | 控制表及导入/发布所需写权限 | 仅查询 `api_v1_*` 视图 |
| 是否可执行 DDL | 不允许 | 仅迁移流程允许 | 不允许 |
| 是否暴露公网 | 不允许 | 不允许 | 按投屏环境开放 |
| 故障影响 | 新预测暂不可用，旧预测/统计仍可查 | 新数据不能发布，旧版本仍可查 | 大屏查询受影响 |
| 发布节奏 | 跟随训练/预测批次 | 跟随数据批次 | 跟随 API 版本 |

## 5. 内部逻辑分层

三个程序均采用端口适配器思想，业务规则不直接依赖 Flask、MySQL 驱动、机器学习框架或 Sqoop 命令。

```text
HTTP/CLI Adapter
      -> Application Service
          -> Domain Policy
              -> Repository / Importer / Validator / Model Port
                  -> MySQL / Hive / Sqoop / File / ML Framework Adapter
```

### 5.1 公共内核 `shared-kernel`

只放真正稳定、跨服务一致的定义：

- `DatasetCode`、`BatchId`、`DataDate`、`SchemaVersion`、`ModelVersion`、`PredictionHorizon` 等值对象。
- 批次状态枚举、错误码约定、分页模型、时间和金额序列化规则。
- 追踪 ID 生成与日志字段约定。

不得放入数据库连接、Flask 上下文、具体表模型、模型实现或接口 DTO，避免三个程序重新耦合。

### 5.2 数据库管理服务内部模块

- `catalog`：登记数据集、粒度、主键、字段版本和上游来源。
- `import_jobs`：创建与执行导入任务，选择 Sqoop/文件等适配器。
- `staging`：把新批次写入临时区，不直接污染已发布结果。
- `quality`：执行行数、唯一性、空值、范围、关联和汇总一致性校验。
- `publication`：控制发布指针或按日期原子替换。
- `rollback`：恢复到上一可用批次，不反向修改 Hive ADS。
- `view_registry`：记录视图版本、依赖和兼容状态。
- `audit`：记录谁在什么时间触发了什么管理动作及结果。

### 5.3 查询后端内部模块

- `dashboard`：大屏总览和组合查询用例。
- `revenue`：费用、营收和成本收益主题。
- `charging`：充电量、负荷、时段和会话主题。
- `stations`：站点地图、排行、效率和详情主题。
- `devices`：电桩状态和健康分布主题。
- `audience`：用户分层和画像；数据不满足时不启用。
- `prediction`：已发布预测结果、模型版本和预测时域查询。
- `metadata`：当前数据日期、批次、更新时间和质量摘要。

每个模块按以下顺序处理请求：

```text
参数校验 -> 用例权限/范围检查 -> 查询一个或多个视图
         -> 内部聚合/排序/补零 -> DTO 映射 -> 统一响应
```

### 5.4 机器学习流水线内部模块

- `feature_contract`：读取固定版本的 ADS 特征契约，不在训练代码中散落 Hive 字段名。
- `dataset_builder`：按时间切分训练、验证和测试集，防止未来信息泄漏。
- `training`：通过统一训练端口选择算法和超参数。
- `evaluation`：计算 MAE、RMSE、MAPE 等指标，并保存与基线模型的对比。
- `model_registry`：登记模型版本、特征版本、训练区间、指标和制品位置。
- `promotion`：只有达到门槛的模型才能标记为活动模型。
- `inference`：按站点和 1h/6h/24h 时域批量产生离线预测。
- `prediction_validation`：检查预测覆盖率、范围、时间连续性和模型版本。
- `export`：输出预测数据和 manifest，交由管理服务发布；不直接写 `rpt_*` 表。

模型文件存放在文件系统或对象存储，MySQL 只登记模型元数据、制品 URI 和校验值，不把模型二进制写入结果表。

## 6. 数据库逻辑设计

### 6.1 数据库和账号

基础阶段只建设一个 MySQL 数据库：

```text
ncs_analytics
```

使用前缀区分逻辑区域，避免过早拆成多个数据库造成跨库迁移和授权复杂度：

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `ctl_` | 批次、发布、质量、数据集和审计控制 | `ctl_import_batch` |
| `ml_` | 模型、训练和预测运行元数据 | `ml_model_version` |
| `stg_` | 当前待校验的临时数据 | `stg_station_day` |
| `rpt_` | 已发布、面向查询优化的结果表 | `rpt_station_day` |
| `api_v1_` | 查询后端唯一允许依赖的稳定视图 | `api_v1_station_rank` |

建议预留四个数据库账号：

- `ncs_migrator`：仅迁移期间使用，拥有受控 DDL 权限。
- `ncs_data_admin`：供管理服务使用，拥有控制表和数据发布所需权限。
- `ncs_view_owner`：作为视图定义者，仅用于权限归属，不允许应用登录。
- `ncs_query_ro`：供查询后端使用，只能 `SELECT` 已授权的 `api_v1_*` 视图。

密码只通过环境变量或密钥管理设施注入，不写入仓库。

### 6.2 控制表

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `ctl_dataset` | 数据集登记 | `dataset_code`、`grain`、`owner`、`enabled` |
| `ctl_dataset_schema` | 输入结构版本 | `dataset_code`、`schema_version`、`schema_hash` |
| `ctl_import_batch` | 导入批次与状态机 | `batch_id`、`data_date`、`status`、`started_at`、`finished_at` |
| `ctl_import_manifest` | 上游交付清单 | 源表/分区、行数、校验值、导出方式 |
| `ctl_quality_result` | 每条质量规则的结果 | `batch_id`、`rule_code`、`severity`、`actual_value` |
| `ctl_publication` | 当前可见批次或日期版本 | `dataset_code`、`active_batch_id`、`published_at` |
| `ctl_view_registry` | API 视图登记 | `view_name`、`api_version`、`contract_hash` |
| `ctl_audit_log` | 管理动作审计 | `actor`、`action`、`target`、`result`、`trace_id` |
| `ml_model_version` | 模型版本和评估结果 | `model_version`、`feature_version`、`metrics_json`、`artifact_uri` |
| `ml_training_run` | 训练运行状态 | `training_run_id`、训练/验证区间、状态、参数摘要 |
| `ml_prediction_run` | 预测运行与覆盖范围 | `prediction_run_id`、`model_version`、`horizon`、`status` |

### 6.3 结果表候选

结果表按查询粒度设计，不把 Hive 明细全量复制到 MySQL。以下是逻辑模型，最终字段取决于 ADS 契约：

| 结果表 | 粒度 | 主要指标/维度 | 对应大屏 |
| --- | --- | --- | --- |
| `rpt_dashboard_snapshot` | 数据日期/批次 | 会话、充电量、费用、活跃站点、异常率 | 顶部总览 |
| `rpt_revenue_day` | 日期/区域/站点 | 充电费用、充电量、订单数 | 费用与电量趋势；V1 不存无来源的服务费/利润 |
| `rpt_charge_hour` | 日期/小时/区域/站点 | 充电量、会话数、负荷 | 24 小时分布、负荷趋势 |
| `rpt_station_day` | 日期/站点 | 使用率、订单、充电量、费用、在线率 | 站点排行、运营效率 |
| `rpt_station_snapshot` | 批次/站点 | 经纬度、桩数、空闲数、故障数、当前状态 | 地图、站点详情 |
| `rpt_charger_status` | 批次/状态/类型 | 数量、占比 | 电桩状态分布 |
| `rpt_user_segment` | 数据日期/分层 | 用户数、次数、时长、充电量、消费 | 用户分层/画像（条件启用） |
| `rpt_battery_health` | 数据日期/健康等级 | 数量、占比、异常率 | 电池健康（条件启用） |
| `rpt_prediction_load` | 预测批次/站点/目标时间/时域 | 预测负荷、预测空闲桩、上下界、模型版本 | 负荷智能预测 |

所有结果表至少包含：

- 完整粒度字段和对应唯一约束。
- `batch_id`、`data_date`、`source_updated_at`、`loaded_at`；预测表还需 `model_version`、`generated_at` 和 `target_time`。
- 明确单位的指标字段；金额使用 `DECIMAL`，比例统一约定为 0～1 或 0～100。
- 可追溯到 ADS 数据集与结构版本的信息。

### 6.4 面向查询的稳定视图

不建立一个覆盖所有图表的巨型视图。每个视图对应一个稳定查询主题：

| 视图 | 目标 | 主要筛选条件 |
| --- | --- | --- |
| `api_v1_dashboard_overview` | 总览指标；V1 不含同比/环比 | `data_date`、`region_id` |
| `api_v1_revenue_trend_daily` | 充电费用与电量趋势 | 日期范围、区域/站点 |
| `api_v1_charge_hourly` | 小时充电量和会话分布 | `data_date`、区域/站点 |
| `api_v1_charger_status` | 在用/空闲/故障数量与占比 | 数据批次、区域/站点 |
| `api_v1_station_rank` | 站点效率或营收排行 | 指标、日期范围、Top N |
| `api_v1_station_map` | 地图点位与当前摘要 | 区域、状态、地图范围 |
| `api_v1_station_detail` | 单站综合详情 | `station_id`、日期范围 |
| `api_v1_user_segment` | 用户分层统计 | `data_date`、分层类型 |
| `api_v1_battery_health` | 电池健康等级分布 | `data_date`、区域 |
| `api_v1_prediction_load` | 1h/6h/24h 预测 | 站点、预测批次、时域 |
| `api_v1_prediction_model_info` | 活动模型公开摘要 | 模型代码、活动版本 |
| `api_v1_data_status` | 当前数据日期、更新时间和质量状态 | 数据集 |

视图规则：

- 视图列名即查询后端的数据访问契约，使用稳定英文 `snake_case`。
- 视图隐藏 `stg_*`、物理表主键和内部批次细节，只暴露业务字段与必要元数据。
- 视图使用受控的 `SQL SECURITY DEFINER`，定义者为不可登录的 `ncs_view_owner`，避免查询账号获得底表权限；迁移时必须检查 definer，不能使用个人或 `root` 账号。
- `api_v1_*` 不做破坏性字段变更；新增字段应保持旧列可用。
- 不兼容变更创建 `api_v2_*`，查询后端按接口版本逐步迁移。
- 视图只读取已发布数据；处于导入、校验或失败状态的批次对查询端不可见。
- 数据库视图不负责参数化 Top N、复杂权限和跨主题编排，这些逻辑留在查询后端。

### 6.5 数据发布策略

根据数据集类型使用两种方式：

1. **快照型数据**：结果表保留 `batch_id`，`ctl_publication.active_batch_id` 指向当前版本，视图只读活动批次。切换指针即可发布或回滚。
2. **日期分区型数据**：先导入 staging 并校验，再在一个事务中替换指定 `data_date` 的结果数据，同时更新发布记录。

发布状态机：

```text
CREATED -> IMPORTING -> IMPORTED -> VALIDATING -> VALIDATED
        -> PUBLISHING -> PUBLISHED

任一步失败 -> FAILED
已发布版本 -> ROLLED_BACK（仅表示不再活动，数据保留供审计）
```

不得在未完成质量校验时发布。发布失败时，旧批次继续对查询后端可见。

## 7. 上游 ADS 与机器学习对接设计

### 7.1 上游交付契约

每个数据集必须同时交付数据和 manifest：

```json
{
  "datasetCode": "station_day",
  "schemaVersion": "1.0",
  "dataDate": "2026-09-12",
  "source": {
    "hiveTable": "ncs_ads.ads_station_day",
    "partition": "dt=2026-09-12"
  },
  "grain": ["data_date", "station_id"],
  "rowCount": 105,
  "checksum": "optional-sha256",
  "generatedAt": "2026-09-12T18:00:00+08:00"
}
```

manifest 中的表名只是导入适配器配置，不进入查询后端。

### 7.2 导入适配器

管理服务定义统一的 `DatasetImporter` 端口，首批实现可选：

- `SqoopImporter`：适合环境已有 Sqoop、表结构稳定的批量导入。
- `FileImporter`：Hive 导出 CSV/TSV/Parquet 后再装载，便于本地开发和问题复现。
- `JdbcImporter`：仅在网络、驱动和数据量允许时作为替代方案。

选择导入方式只影响适配器，不影响批次、质量、发布和查询逻辑。

### 7.3 必须校验的内容

- manifest 数据集、日期、结构版本是否受支持。
- 输入列与登记 schema 是否一致。
- 行数是否与 manifest 一致。
- 粒度字段是否为空、是否唯一。
- 金额、充电量、时长、SOC、比例等是否在合理范围。
- 站点维度关联覆盖率是否达到阈值。
- 同一日期汇总值与 ADS 校验值是否一致。
- 关键数据质量问题是否被显式标记。

已知源数据时间问题必须保留：`record_time` 精度损失和 `created` 异常年份不能在结果库中静默猜测修复。

### 7.4 机器学习输入契约

机器学习流水线只读取专门的特征数据集，不直接依赖 ODS/DWD 明细，也不在训练代码里自行解释脏数据。负荷预测输入至少需要：

- `station_id`、时间窗口和预测目标。
- 历史充电量、会话数、占用/空闲桩数量等时序特征。
- 站点容量、桩类型和区域等相对稳定特征。
- 天气、节假日等外部特征只有在来源稳定且训练、预测两端都可获得时才启用。
- `feature_version`、统计时间范围、生成时间和质量状态。

时间字段精度无法恢复时，不允许凭规则伪造高频时序特征；应降低预测粒度、改用可靠时间字段或暂停相关模型。

### 7.5 模型与预测输出契约

模型登记至少包含：

- `model_code`、`model_version`、算法类型和制品校验值。
- `feature_version`、训练/验证/测试时间区间。
- 评估指标、基线指标、启用门槛和评估时间。
- 模型制品 URI、创建时间和活动状态。

预测 manifest 在通用数据 manifest 基础上增加：

```json
{
  "datasetCode": "prediction_load",
  "schemaVersion": "1.0",
  "modelVersion": "load_forecast_20260912_01",
  "featureVersion": "station_load_features_v1",
  "predictionRunId": "pred_01J...",
  "generatedAt": "2026-09-12T18:00:00+08:00",
  "horizons": ["1h", "6h", "24h"],
  "targetTimeRange": {
    "start": "2026-09-12T19:00:00+08:00",
    "end": "2026-09-13T18:00:00+08:00"
  },
  "rowCount": 7560
}
```

预测数据必须先进入 staging，完成站点覆盖、目标时间连续性、数值范围和模型版本校验后，再与普通 ADS 结果一样发布。

### 7.6 训练与大屏查询解耦

- 查询请求不触发训练或推理。
- 模型切换只影响后续预测批次，不修改历史预测。
- 大屏默认读取最新已发布预测；需要复盘时可由内部管理接口指定历史批次，公开 API 不暴露任意批次选择。
- 预测缺失时返回明确的 `UNAVAILABLE` 或最后可用预测及其生成时间，不能把历史值伪装成最新预测。
- 预测曲线必须能与同时间段的历史实际值区分，API 返回 `seriesType`、`modelVersion` 和 `generatedAt`。

## 8. 查询后端与前端对接设计

### 8.1 API 基线

- API 前缀：`/api/v1`。
- 字段格式：JSON 使用 `camelCase`，数据库视图使用 `snake_case`，映射在 DTO 层完成。
- 时间：ISO 8601；统计日期使用 `YYYY-MM-DD`；明确时区为 `Asia/Shanghai`。
- 金额：服务内部使用定点数，API 统一返回十进制字符串，避免前端二进制浮点误差。
- 比例：统一返回 0～1 的十进制字符串，由前端按接口提供的精度格式化百分比。
- 列表：必须有 `limit` 上限；普通列表使用分页，图表点数使用时间粒度和最大范围限制。
- 空数据：返回成功和空集合，不用系统错误表示“没有数据”。

统一响应草案：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "meta": {
    "traceId": "01J...",
    "dataDate": "2026-09-12",
    "generatedAt": "2026-09-12T18:30:00+08:00"
  }
}
```

### 8.2 前端接口候选

这些接口用于预留路由和内部用例，下一步再确定字段级契约：

### 8.3 查询后端内部完成的逻辑

为降低前端耦合，以下逻辑由查询后端负责：

- 日期范围默认值、最大查询跨度和粒度选择。
- 指标白名单到视图列的映射，禁止前端提交任意列名或排序 SQL。
- 区域、站点、状态等筛选参数校验。
- 多视图结果组合为一个页面 DTO，但避免一个接口返回整站全部数据。
- 缺失日期/小时补零、固定枚举排序和 Top N 截取。
- 单位、精度、时间格式和数据库字段到 API 字段的转换。
- 空数据、部分数据、数据过期等状态表达。
- 错误码、追踪 ID、日志和性能计时。
- 必要的短时缓存；缓存键必须包含数据日期和筛选条件。
- 历史实际曲线和预测曲线的时间对齐、序列类型标识及预测缺口表达。
- 按 `cutoffHour` 切断未来实际值，回测数据不得混入线上预测响应。
- 保留负电流的方向语义；`avgMaxTemperature` 不得改名或展示为普通平均温度。

以下逻辑不应交给前端：

- 拼接 SQL、推断数据日期、计算复杂统计口径。
- 识别活动批次、过滤失败批次。
- 将异常年份或丢失时间自行修正。
- 合并来自多个数据源且可能口径不一致的数据。

### 8.4 前端需要提供或确认

- 页面和组件清单、组件刷新频率。
- 每个指标的名称、单位、口径和对比方式。
- 过滤条件、默认值、联动关系和最大时间范围。
- 图表需要的排序、补零、分组和 Top N 行为。
- 空数据、部分失败、数据过期时的展示规则。
- 投屏分辨率、是否自动轮播、全屏刷新策略和断网时保留最后画面的要求。
- 地图坐标系要求；腾讯地图通常涉及 GCJ-02，不能直接假定 ADS 坐标可用。
- 是否需要登录鉴权、不同角色的数据范围控制。

### 8.5 大屏投射运行策略

大屏投射按“浏览器全屏展示 + API 周期拉取”设计，不依赖 Qt，也不要求后端主动控制投影设备。

- 首屏先请求 `/api/v1/meta/data-status`，再并行请求各图表接口，避免一个超大接口导致整屏一起失败。
- 统计类接口按 ADS 发布频率刷新；预测接口按预测批次刷新，不能统一按秒轮询。
- API 返回 `ETag` 或可比较的 `dataVersion`，数据未变化时减少重复传输和 ECharts 重绘。
- 单个组件失败时保留该组件最后一次成功数据并显示更新时间，其他组件继续刷新。
- 全局状态区必须显示实际数据日期、预测生成时间和模型版本，避免把离线结果展示成实时数据。
- 页面应提供固定的演示数据开关，但演示数据必须与真实 API 模式明显隔离，默认不得启用。
- 后端不保存屏幕布局、颜色或动画逻辑；这些属于大屏前端。后端只保证数据、状态和版本契约。

## 11. 错误处理与可靠性

### 11.1 错误分类

- `VALIDATION_*`：请求参数或 manifest 不合法。
- `DATASET_*`：数据集未知、schema 不兼容、粒度冲突。
- `IMPORT_*`：导入失败、行数不符、重复执行冲突。
- `QUALITY_*`：阻断级质量规则失败。
- `PUBLICATION_*`：非法状态转换、发布或回滚失败。
- `MODEL_*`：模型版本、评估、制品或启用状态不合法。
- `PREDICTION_*`：预测覆盖不完整、时域错误或预测结果不可用。
- `QUERY_*`：查询超时、范围过大、数据暂不可用。
- `DEPENDENCY_*`：MySQL、Hive/导出端或其他依赖不可用。
- `INTERNAL_*`：未分类内部错误。

### 11.2 幂等和重试

- 导入任务以 `dataset_code + data_date + schema_version + source_batch` 或调用方幂等键去重。
- 仅对明确可重试的连接/超时错误自动重试，并使用退避。
- 数据校验失败不自动重试，必须修复数据或规则后重新创建/执行任务。
- 发布操作重复调用应返回已有结果，不重复写数据。

### 11.3 降级原则

- 新批次失败不影响旧批次查询。
- 某扩展主题不可用时不影响基础总览接口。
- 查询接口不把数据库堆栈信息返回前端。
- 数据过期时可返回最后可用数据，但 `meta` 必须标记实际 `dataDate` 和新鲜度状态。

## 12. 安全设计

- 前端只能访问查询后端，不能持有数据库凭据。
- 查询账号只授权明确的 `api_v1_*` 视图。
- 管理服务不暴露任意 SQL、任意文件路径和任意表名输入。
- 所有 SQL 参数化；动态指标、排序字段和粒度使用白名单映射。
- 管理动作要求鉴权、授权和审计；回滚等动作可再增加二次确认机制。
- 日志不记录密码、Token、完整连接串或敏感个人信息。
- 用户手机号、余额等交易数据默认不进入分析结果库；确有分析需求时先做最小化和脱敏。
- 模型制品必须校验来源和哈希，加载时不执行来源不明的序列化对象。

## 13. 性能与可观测性

基础目标在拿到真实并发和数据量后量化，当前先遵循：

- MySQL 只保存大屏需要的聚合结果，避免在线扫描明细。
- 索引围绕视图过滤与排序字段设计，先用执行计划验证再增加。
- 地图和排行接口设置最大返回数量。
- 慢查询记录视图名、耗时、行数和 traceId，不记录完整敏感参数。
- 暴露请求量、错误率、延迟、数据库连接池、导入耗时、质量失败数和数据新鲜度指标。
- 记录模型版本、预测批次、特征版本、预测覆盖率和实际值回流后的误差变化，用于发现模型漂移。
- 大屏轮询频率由数据刷新频率决定；日批数据不应被前端按秒刷新。

## 15. 分阶段实施计划

### 阶段 A：契约确认

1. 收集 ADS 表、字段、样例数据、分区和刷新方式。
2. 收集大屏组件清单和交互需求。
3. 建立“组件 -> API -> 视图 -> 结果表 -> ADS/预测数据 -> 模型版本”的映射表。
4. 确认负荷预测目标、预测时域、训练数据范围和验收指标。

输出：`data-contract.md` 和 `api-contract.md` 初稿。

### 阶段 B：数据库骨架

1. 建立 `ncs_analytics`。
2. 建立控制表和第一批 `rpt_*` 结果表。
3. 建立第一批 `api_v1_*` 视图和最小权限账号。
4. 准备迁移、回滚和契约检查。

输出：可重复执行的数据库迁移，不手工改共享数据库。

### 阶段 C：管理服务骨架

1. 实现数据集目录、批次状态机和 manifest 校验。
2. 实现一个导入适配器。
3. 实现 staging、质量校验、发布和回滚。
4. 开放受控内部接口和 CLI。

输出：一个数据集可端到端发布，失败时旧数据仍可查询。

### 阶段 D：机器学习流水线

1. 固化特征数据契约和时间切分规则。
2. 建立可复现的基线模型、训练配置和评估流程。
3. 登记模型版本，实现 1h/6h/24h 离线预测。
4. 输出带 manifest 的预测数据，并通过管理服务完成校验和发布。

输出：可追溯的活动模型和一批可供大屏查询的已发布预测结果。

### 阶段 E：查询服务与投屏联调

1. 实现应用工厂、统一响应、错误处理和数据库只读连接。
2. 实现总览、趋势、状态分布、站点排行、负荷预测和数据状态。
3. 使用 DTO 隔离视图列和 API 字段。
4. 完成组件独立刷新、旧数据保留和数据/模型版本展示的投屏联调。
5. 增加单元测试、集成测试和契约测试。

输出：统计和机器学习结果可在 Web 大屏稳定投射。

### 阶段 F：扩展与优化

- 站点地图、详情、用户画像、电池健康和其他模型按数据可用性启用。
- 根据真实查询计划补充索引、缓存和预聚合。
- 根据模型监控结果增加漂移检查、重训策略和模型回退。
- 补齐监控、部署和运行手册。

## 16. 下一步接口设计的输入清单

进入字段级接口设计前，至少需要以下信息：

1. ADS 表清单、DDL、分区和每表 10～20 行脱敏样例。
2. 每个指标的中文名称、业务定义、计算公式、单位和小数精度。
3. 大屏组件清单或原型图，注明筛选、联动和刷新频率。
4. 站点、电桩、会话、订单等 ID 在 ADS 和预测数据中的映射方式。
5. 数据刷新周期，以及全量、增量或按日期重跑策略。
6. MySQL 版本和部署环境；Sqoop 是否实际可用。
7. 是否需要登录鉴权、角色和数据范围控制。
8. 负荷预测标签、特征、训练时间范围、预测频率和验收指标。
9. 用户画像、电池健康、成本和舆情等扩展数据是否真实存在。

## 17. 当前未决项

以下问题不阻塞逻辑架构，但会影响下一步具体接口和表字段：

- ADS 的实际表名、字段和统计粒度。
- 大屏顶部总览指标的准确口径和活跃站点统计周期；同比/环比不进入 V1。
- 站点状态在 ADS 中的刷新周期；本阶段不接入 Qt 或交易系统实时状态。
- 负荷预测目标究竟是功率、充电量、会话数还是空闲桩数量。
- 预测时间粒度、更新频率、模型验收阈值和基线模型。
- 成本、用户平台、舆情和电池健康等扩展数据是否存在可靠来源。
- 经纬度采用 WGS-84、GCJ-02 还是其他坐标系。
- 调度器由谁负责，以及其调用 HTTP 还是 CLI。

在这些事项确认前，可以搭建框架、控制表和契约模板，但不能把演示图中的示例数字或字段当成正式业务定义。

## 18. 接口设计就绪标准

满足以下条件后进入下一步字段级接口设计：

- 基础大屏组件及优先级已确定。
- 每个组件都有对应数据来源和统计粒度。
- ADS 输入、机器学习特征/预测契约与结果库逻辑表能一一映射。
- `api_v1_*` 视图边界已确认。
- 机器学习流水线、查询后端和数据库管理服务的接口范围无重叠。
- 负荷预测目标、时域、模型版本和验收指标已确认。
- 时间、金额、比例、空值、错误和分页约定已确认。
- 未确定数据源的扩展主题被明确标为条件启用，不阻塞基础交付。
