## 1. 结论

需要更新数据和文档，不需要修改当前 ADS 导入表结构。v3.2 包内面向本项目的 `contract_v2` 仍使用 `schemaVersion=2.2.0`、`metricVersion=2.2.0` 和原有 18 个数据集，字段顺序、主键和文件名与现有适配器一致。已使用现有 `AdsV23PackageReader` 和 `AdsV23Importer` 完成整包 SQLite 导入，18 个数据集全部发布成功。

“上游完整包 v3.2”与“下游数据合同 2.2.0”是两个版本维度，不能混写。现有代码文件名 `ads_v23_*` 和旧称“ADS v2.5”是兼容历史，不表示当前仍使用旧数据包。

## 3. 与上一交付的关键变化

1. 业务展示时间统一到 2019，不再使用 `YEAR_PLUS_2000` 的 2014/2015 展示口径。
2. 订单经过 DWD 质量规则后从 5,000 条保留 4,855 条；排除 66 条非正电量、29 条超过 24 小时和 50 条平均功率超过 120 kW 的记录。
3. 正电量零费用订单保留并标记为费用缺失/脱敏，不填造费用；因此费用总额不能与旧包直接比较。
4. `load_hourly` 改为按订单覆盖自然小时的秒数分摊电量，`allocation_method=DURATION_PRORATED`，并保持小时连续。
5. 工作日/周末使用上游 `weekday` 字段，`sourceWeekdayRule=SOURCE_WEEKDAY`。
6. 当前总览为 4,855 单、28,547.67 kWh、570.05 CNY、144 用户、105 个活跃站点。

## 4. 对现有代码的影响

- ADS 导入器：无需改 Schema，现有 18 数据集合同已通过真实包验证。
- MySQL：需要把 v3.2 `02_结果数据/contract_v2/` 作为新全量批次导入，成功后原子替换活动发布。
- Flask/前端：接口路径和 DTO 无需改变；页面数据日期、总量、趋势和排行会随新批次变化。
- Shell：应由上游流水线成功后把 `contract_v2` 目录打包并生成 `.ready` 标记，再交给本项目同步；不得直接执行交接包中的上游 SQL。
- 模型：旧测试模型是按上一版负荷序列和日历口径交付。它可能通过技术推理，但在 `DURATION_PRORATED + UPSTREAM_FIXED_YEAR_2019` 新口径下不能宣称模型有效；模型同学应使用新数据重新训练并交付新版本、权重哈希和输入合同。

## 5. 上游包内部待确认问题

包内最终结果 Manifest、`README_先看这里.md` 和 `数据包说明_v3.2.md` 一致指向 4,855 条有效订单、2,323 条过程记录和 8,719 小时序列，应作为当前事实。

但 `01_流水线/版本说明与故障排查_v3.2.md` 的“本次验证结果”仍写有 4,677 条有效订单、2,328 条过程记录和 8,674 小时序列，同一文件后文又写回 4,855/2,323。该段属于旧回归残留，应由上游修正文档；本项目不据此改写数据。

此外，完整包标记为 v3.2，但 `01_流水线/README.md` 标题仍为流水线 v2.7。这可以是内部流水线版本，但上游应明确“包版本、流水线版本、数据合同版本”三者关系。

## 6. 当前接入步骤

1. 将完整包中的 `02_结果数据/contract_v2/` 单独压缩成一个交付包。
2. Windows 手工入口将包放入 `data_exchange/packages/` 后运行 `import_data_package.cmd`；虚拟机自动入口按 README 的 `.part → .zip → .ready` 协议投递。
3. 导入成功后检查数据状态、总览、18 个发布记录及主要查询 API。
4. 使用新 `load_hourly` 导出模型数据集；收到新模型版本后重新登记、激活和发布预测。
