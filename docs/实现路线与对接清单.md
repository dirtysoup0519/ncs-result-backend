# NCS 结果库与后端实现路线及对接清单

> 状态：实施基线  
> 适用范围：机器学习流水线、MySQL 结果库、数据库管理服务、大屏查询后端  
> 不包含：ODS/DWD/DWS/ADS 生产脚本、Qt、交易业务、设备控制和大屏视觉实现

## 1. 实施原则

1. 先建设不依赖外部环境的公共骨架和契约测试，再接入真实数据。
2. 真实 DDL、字段映射和业务指标不得根据课件或演示数据猜测，必须以已确认的 ADS DDL、样例和指标口径为准。
3. 查询后端只读取 `api_v1_*` 视图；数据库管理服务负责导入、校验、发布和回滚；机器学习流水线不直写已发布结果表。
4. 每一步都必须有独立验收条件。上一步的阻断项未关闭时，只能实现不依赖该项的部分。
5. 每次具体实现前，先列出“本次可内部完成”和“需要你对接”两部分；需要外部材料时明确负责人、材料格式、截止点和缺失影响。

## 2. 推荐实施顺序

### 步骤 0：冻结第一阶段范围

目标：把首轮开发限制在能形成端到端闭环的最小集合。

第一阶段建议只包含：

- 数据状态与能力查询。
- 总览指标。
- 日趋势与 24 小时分布。
- 站点排行和站点基础列表。
- 负荷预测结果查询；如果特征和预测合同尚未确认，则先保留能力开关，不返回演示假数据。

内部完成：整理 P0 接口、视图和数据集清单，冻结命名和版本规则。

需要你对接：

| 对接方 | 需要确认 | 期望交付物 | 缺失影响 |
| --- | --- | --- | --- |
| 产品/大屏负责人 | 首屏组件、筛选条件、刷新频率、空数据展示 | 组件清单或原型标注 | 无法冻结 P0 API |
| 项目负责人 | 匿名投屏或登录投屏 | 鉴权结论 | 无法确定访问控制 |

验收：每个 P0 组件都能映射到一个 API 和一个数据集，不包含 Qt 或交易业务功能。

### 步骤 1：建立工程骨架与公共合同模型

目标：在不依赖真实 ADS 和 MySQL 的情况下，建立三个程序的边界。

内部完成：

- 建立 `shared-kernel`、`data-admin-service`、`analytics-query-api`、`ml-pipeline` 的目录和依赖边界。
- 定义配置加载、日志、追踪 ID、统一错误、分页、时间、金额、比例、批次状态等公共模型。
- 建立测试、格式检查和本地启动入口。
- 提供 `.env.example`，不写入真实连接信息。

需要你对接：无。Python 和依赖版本可以先采用项目基线，后续根据部署环境调整。

验收：各模块可独立导入和运行最小测试；查询服务不能依赖管理服务内部实现；仓库中没有真实凭据。

### 步骤 2：固化数据集 Manifest、Schema 和质量规则

目标：先固定“上游如何交付”，再设计真实表结构。

内部完成：

- 实现数据集 Manifest、Schema 版本、字段定义、唯一键、粒度和校验和模型。
- 实现 schema、非空、唯一性、范围、行数和关联覆盖率等质量规则接口。
- 提供统计数据、特征数据和预测数据的合同样例与契约测试。

需要你对接：

| 对接方 | 需要材料 | 最低要求 | 缺失影响 |
| --- | --- | --- | --- |
| 数仓负责人 | ADS/DWS DDL、分区、真实脱敏样例、刷新方式 | 表名、字段、类型、粒度、主键候选、数据日期 | 不能冻结真实结果表 |
| 数仓负责人 | ID 映射规则 | `station_id`、`pile_id`、`session_id`、`order_id` 的来源和关系 | 站点及预测关联不可靠 |
| 数仓/产品 | 指标口径表 | 公式、单位、精度、空值、零值、同比/环比基准 | API 数值语义不稳定 |

特别需要确认：`fee_ratio` 是 `[0,1]` 还是百分数、缺失小时是否补零、修复时间字段是否带质量标记、零费用订单是否进入收入类指标分母。

验收：每个 P0 数据集有可机器校验的 manifest 和样例；不合格数据能够被拒绝并给出明确原因。

### 步骤 3：实现结果库控制面和版本化迁移

目标：先建设与业务字段相对独立的批次、发布、质量和审计能力。

内部完成：

- 创建数据库迁移框架。
- 实现 `ctl_*` 控制表：数据集、schema、导入批次、质量结果、发布指针、审计记录。
- 实现模型登记和预测运行元数据表的基础结构。
- 定义数据库账号边界：迁移账号、管理服务账号、查询只读账号。

需要你对接：

| 对接方 | 需要确认 | 期望交付物 | 缺失影响 |
| --- | --- | --- | --- |
| 环境负责人 | MySQL 版本、地址、字符集、时区、建库权限 | 环境说明；真实凭据走安全渠道 | 只能在本地数据库验证 |
| 运维/数仓 | ADS 到结果库可用通道 | Sqoop、文件或 JDBC 的可用性和网络权限 | 不能选择正式导入适配器 |

验收：迁移可重复执行；控制表状态转换受约束；查询账号不能写表或读取 staging/控制表中的敏感内容。

### 步骤 4：实现导入、校验、发布与回滚闭环

目标：让一批数据可以安全进入结果库，并以原子方式对查询端可见。

内部完成：

- 实现导入端口和文件/JDBC 基础适配器。
- 实现 `stg_* -> 质量校验 -> rpt_* -> 发布指针` 流程。
- 实现幂等键、失败清理、重跑、发布和回滚状态机。
- 实现内部管理接口或 CLI；第一阶段不开放任意 SQL 和在线 DDL。

需要你对接：数仓负责人提供一批真实可复核数据及对应 manifest；环境负责人确认正式导入方式和调度入口。

验收：同一批次重复导入不产生重复数据；未通过质量校验的批次不能发布；回滚后查询恢复上一可用版本；审计记录完整。

### 步骤 5：实现 P0 结果表和 `api_v1_*` 视图

目标：把上游变化隔离在稳定查询合同之后。

内部完成：

- 根据已确认字段建立 P0 `rpt_*` 表、唯一约束和必要索引。
- 建立 `api_v1_*` 视图，统一字段名、单位、空值和来源元数据。
- 在后端或视图边界完成 0～23 小时补齐等确定性适配；保留 `isObserved` 等质量信息。
- 建立“API 字段 -> 视图列 -> 结果表列 -> 上游字段/指标”的追踪表。

需要你对接：产品、数仓共同签字确认字段映射和指标口径；前端确认坐标系、时间格式、金额/比例展示规则。

验收：查询账号只访问视图即可完成 P0 查询；视图切换批次时不会暴露半批数据；字段追踪链完整。

### 步骤 6：实现大屏查询后端

目标：向前端提供稳定、只读、可降级的 REST API。

内部完成：

- 搭建应用工厂、配置、数据库连接、仓储、服务和 DTO 分层。
- 实现能力、数据状态、总览、趋势、小时分布、站点排行和站点列表接口。
- 实现参数校验、查询上限、统一错误、超时、ETag 和新鲜度元数据。
- 提供 OpenAPI、契约测试和集成测试。

需要你对接：

| 对接方 | 需要确认 | 联调重点 |
| --- | --- | --- |
| 前端负责人 | 请求参数和响应样例 | 字段、单位、排序、颜色无关的状态枚举 |
| 前端负责人 | 空数据、过期数据、单组件失败 | 是否保留最后成功数据及提示方式 |
| 部署负责人 | 域名、跨域、鉴权和限流边界 | 浏览器访问与投屏网络 |

验收：正常、空数据、非法参数、过期数据和数据库失败均有确定响应；任一组件失败不破坏其他组件接口。

### 步骤 7：实现机器学习最小闭环

目标：实现可复现、可评估、可发布的离线负荷预测，不把训练放入查询请求。

内部完成：

- 实现特征读取、时间切分、训练、评估、模型登记、离线预测和预测发布端口。
- 建立朴素基线模型，记录数据版本、代码版本、参数、指标和制品哈希。
- 将通过质量门槛的预测批次导入结果库；查询 API 只读取已发布预测。
- 未启用预测能力时返回 `CAPABILITY_DISABLED`，不生成演示假值。

需要你对接：

| 对接方 | 必须确认 | 期望结果 |
| --- | --- | --- |
| 产品/算法 | 预测目标 | 功率、充电量、会话数或空闲桩数量中的明确一项 |
| 数仓/算法 | 特征表和标签 | 字段、粒度、时间语义、质量标记、可用历史范围 |
| 产品/算法 | 预测时域和频率 | 1h/6h/24h 的定义及滚动方式 |
| 产品/算法 | 验收标准 | 基线、MAE/RMSE/MAPE、评估窗口和启用阈值 |
| 环境负责人 | 模型制品位置 | 受控 URI、权限、保留周期和容量 |

验收：同一数据版本与参数可复现；不存在未来数据泄漏；不合格模型不能启用；新预测失败不影响基础统计和上一可用预测。

### 步骤 8：真实环境联调、性能与交付

目标：使用一批真实 ADS 数据跑通完整链路并形成可运维交付物。

内部完成：端到端测试、查询执行计划、必要索引、性能基线、日志指标、备份/回滚说明和运行手册。

需要你对接：数仓确认源端数字，前端完成大屏联调，环境负责人提供测试环境和部署方式，项目负责人确认验收结果。

验收：上游行数和关键汇总值可对账；P0 API 达到约定响应时间；发布、回滚和故障降级演练通过；真实凭据未进入 Git。

## 3. 推荐的近期开发批次

按照风险和依赖，近期按以下小批次推进：

1. `Iteration 1`：工程骨架、公共类型、错误码、配置和测试框架。
2. `Iteration 2`：Manifest、Schema、质量规则和批次状态机。
3. `Iteration 3`：控制表迁移、仓储端口和本地 MySQL 集成测试。
4. `Iteration 4`：以确认后的 ADS 样例实现首个数据集导入、发布和回滚。
5. `Iteration 5`：首批 `api_v1_*` 视图及总览/趋势 API。
6. `Iteration 6`：站点、小时分布、数据状态接口及前端联调。
7. `Iteration 7`：负荷预测基线、评估、登记和发布闭环。
8. `Iteration 8`：真实环境对账、性能优化、运行手册和验收。

## 4. 每次实现时的对接提示格式

后续每次开始具体实现，我会先给出：

```text
本次目标：
本次内部完成：
需要你对接：
  - 对接方：
  - 需要材料/决定：
  - 最晚需要时间：
  - 缺失时的降级方案或阻断影响：
本次不做：
验收方式：
```

实现结束时，我会明确区分：已完成、使用假实现/本地样例完成、等待外部确认、被外部依赖阻断。不会把“接口已预留”描述成“链路已打通”。

## 5. 当前第一步

下一步直接开始 `Iteration 1`：搭建工程骨架和公共合同模型。该步骤不需要等待上游、前端或环境负责人，可以独立完成。

与此同时，你可以并行向相关人员收集以下材料，供 `Iteration 2～5` 使用：

1. 数仓负责人：ADS/DWS DDL、真实脱敏样例、刷新周期、ID 映射和指标口径。
2. 前端/产品负责人：首屏组件清单、筛选参数、空数据/错误/过期数据展示规则、地图坐标系。
3. 环境负责人：MySQL 版本、Python 版本、网络权限、正式导入方式和部署方式。
4. 算法/产品负责人：预测目标、时域、时间粒度、特征与标签、评估阈值。
